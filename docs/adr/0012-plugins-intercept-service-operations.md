# Plugins intercept Service Layer operations through Change Sets

_Implementation status (2026-10-15): built. `doctor --fix` now runs each fix pass as a `doctor.fix` operation through this pipeline, so the sentence below about repositories describes the time of the decision. The error policy in the fifth paragraph is amended by [ADR-0020](0020-plugin-execution-and-data-contracts.md) §5, and [ADR-0019](0019-coordinated-recoverable-commits.md) sets how a Change Set is coordinated and committed; both are accepted and built. The rationale below is unchanged._

Plugins can guard, transform, replace and react to every core operation, such as creating, moving or deleting a Story. They do this in the Service Layer. Both the CLI and the TUI use that layer, so one handler covers both surfaces, and Plugins see the intent of a change (a move, not only a written file). We rejected the storage layer, which shows only raw writes, and handlers per surface, which would have to be written twice. `doctor --fix` writes through repositories today; its fixes become operations of their own.

An operation does not write files while it runs. It collects a Change Set: every record that it creates, changes or deletes, with the record before and after the change. Guards and transforms receive the operation's name, its input and the Change Set before anything is saved. A guard can reject the operation with a message, and then nothing is saved. A transform can change the Change Set. A replacement runs instead of the core operation. After the save, reactions receive the same Change Set. Because Plugins see the record changes and not only the operation's name, they also see the Stories that `stages remove --move-to` moves, that `assignees remove` edits, and that `doctor --fix` renumbers.

A Plugin's own operations, such as deleting an Epic or a Board Spec, are operations too. Their Change Sets can include the Plugin's files, and other Plugins can guard, transform and react to them. A reaction acts only outside Rowbly's data, for example by running git. A change to Rowbly data belongs in a transform, so one user action makes one Change Set, which is saved once. Command mode waits for reactions before it exits; the TUI runs them after the save without blocking the screen.

Plugin input reaches an operation through the operation's own input, as `plugins: { <id>: … }`. For example, `stories create --epic auth` and the Epic select in the TUI Story form fill the same input, and the Epics transform writes it into the new Story's bag in the same save. We rejected running the Plugin's change as a second operation, which would save twice.

An error in a guard, a transform or a replacement fails the operation: nothing is saved, the command exits 1, and the error names the Plugin and says how to turn it off. A guard's rejection exits 4, like a refused deletion. With `--json`, both errors carry `details.plugin`. A reaction runs after the save, so an error in a reaction only warns, and the exit code stays 0.

Plugins run in registry order. A Plugin that replaces a core part must declare it. Any other clash makes the later Plugin in the registry fail to load (ADR-0010), for example two Plugins that add the same flag or key, or a Plugin that uses a name core already uses. A Plugin's commands are under one top-level command named after its id (`rowbly epics …`), so its id is the only command name it can clash on. For now only operations can be replaced; replacing a screen or a command will follow the same rule when a Plugin first needs it.

The whole mechanism is built now and tested with fixture Plugins, although Epics and Specs use only part of it. The parts share one pipeline, so building all of them costs little more than building some.
