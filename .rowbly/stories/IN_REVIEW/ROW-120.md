Read the Spec `deterministic-factory`.

## Goal

The manager gives each Stage its class (`work`, `hold` or `invalid`) by a fixed rule and by the factory settings. The supervisor does not classify Stage prompts. A new Stage with a prompt gets workers at once, without a supervisor turn.

## Now

`classifyPrompt` in `src/services/factory-manager/manager-status.ts` gives `invalid` for an empty prompt and `hold` for `BACKLOG` and `DONE`. For all other Stages, it uses the class that the supervisor stored in `state.json` (`prompts`) for the hash of the prompt. A Stage without a stored class is `unclassified`, and the policy (`stageSkipReason` in `src/services/factory-policy/factory-policy.ts`) skips its Stories with the reason `stage prompt not classified` until the supervisor calls `classify_stage`.

## Scope

In scope:

- The rule, in this order:
  1. A class in the new setting `factory.stageClasses` (for example `{ "IN_REVIEW": "hold" }`) applies first. The values are `work` and `hold`.
  2. A Stage with an empty prompt (only white space) is `invalid`.
  3. The first Stage and the last Stage of the board are `hold`.
  4. All other Stages are `work`.
- The class `unclassified` and the skip reason `stage prompt not classified` go away.
- The manager does not read or write the `prompts` key of `state.json`. An old `state.json` with this key stays valid.
- A CLI option sets and clears the class of a Stage: `rowbly factory configure --stage <key> --class <work|hold>` and `rowbly factory configure --stage <key> --clear-class`.
- Remove the supervisor tools `stage_get` and `classify_stage`, the `unclassified` section of the supervisor digest, and the classification rules in `src/config/prompts/SUPERVISOR.md`.
- Update the tests of the policy, the manager and the settings, and the docs of the native factory.
- A CHANGELOG entry.

Not in scope:

- A TUI control for the setting.
- Other supervisor tools (ROW-124 removes the supervisor).
- A worker limit for each Stage.

## Assumptions

- "The first Stage and the last Stage of the board" are the first and the last entries of `stages` in `rowbly.config.json`, enabled or not. Reason: this is the order of the workflow, and a disabled Stage already gets the skip reason `stage unavailable`. In this Project they are `BACKLOG` and `DONE`, so the behaviour of these two Stages does not change.
- The CLI option is `--stage <key> --class <work|hold>` and `--stage <key> --clear-class`. It reuses the existing `--stage` option of `factory configure`. Reason: the Story gives this form as an example, and it follows the pattern of `--stage` with `--clear-worker`.
- `--class` and `--clear-class` cannot be used together with `--story`. Reason: a class applies to a Stage, not to a Story.
- `invalid` is not a value of `factory.stageClasses`. Reason: the Story gives only `work` and `hold`.
- A `factory.stageClasses` entry for a Stage key that a user later deletes stays in the config and has no effect. Reason: the existing `stageWorkerModels` overrides act the same way, and smallest scope.
- The skip reason for a `hold` Stage stays `hold stage`. Reason: the existing policy uses this text.
