Read the Spec `deterministic-factory`.

## Goal

The manager starts the workers itself, from the decisions of the policy. The factory does not open a supervisor session. After this Story, no LLM makes a dispatch decision, and the factory makes no model calls when no worker runs.

## Now

`superviseOnce` in `src/services/factory-manager/supervisor-loop.ts` reconciles the Project, then sends a digest to a Pi supervisor session. The supervisor calls `start_worker` for the `start` and `retry` decisions of the policy. It also keeps holds, notes and report acknowledgements, and the manager rotates its session and applies a backoff to its turns. The Stage classes (ROW-120), the fallback worker models (ROW-121) and the attention from worker problems (ROW-122) are on `main` already.

## Scope

In scope:

- **Dispatch.** On each pass, after the reconcile, the upstream steps, the side steps and network resume, the manager reserves a worker for each `start` and `retry` decision, in the order of `policy.decisions` (the launch order of the policy). It calls `reserveWorker` (`worker-reservation.ts`) with no `model`, no `host` and no `resumeThreadId`.
- **Model and host.** `selectWorkerModel` gives the model from the factory settings (Story override, Stage override, `factory.workerModel`, then `factory.fallbackWorkerModels` when the provider is paused). `placeStory` selects the host. The tag rule of ROW-123 joins `selectWorkerModel` when ROW-123 is complete. This Story does not need it.
- **Fixed request ID.** Each start uses the request ID `<story-id>:<stage>:<attempt>`, with `decision.attempt ?? 1`. A second pass, or a second decision for the same work, cannot start the same work two times.
- **Errors.** A `ConflictError` for one Story (for example a full host, a paused provider, a Story that moved) skips only that Story, with no attention entry. A different error sets the attention entry `dispatch` with `failureText`, and the pass continues with the next decision. A pass with no dispatch error removes the `dispatch` entry.
- **Retry.** A `retry` decision starts a new worker Thread. `resumeNetworkThreads` (network resume) does not change.
- **Release command.** Add `rowbly factory release <story-id>` because `release_story` goes away. It sends the new control command type `release` (with a `storyId` field) to the live daemon, like `dismiss`. The daemon moves the logic of `releaseHeldStory` (without holds) to a manager method, then calls `notify`. A Story that is not parked gives a success with no change. Without a live daemon, the command fails with "Factory is not running", like `resume`. A Story that the user moves or changes is released, as now.
- **Removal.** Remove the supervisor session and its open, rotation, backoff, digest delivery and Thread; `supervisor-tools.ts`; `src/services/supervisor-digest/` and its test; `supervisorMessage()` in `messages.ts`; the holds (`Hold`, `holds`, the `held:` skip reason, the hold deadlines); the notes; the report acknowledgements (`pendingReports`, `markReported`, `deliveredReportIds`, `attemptedHash`, `acknowledgedHash`, `unanswered`, `nextWakeAt`, `wakeCount`, `supervisorBorn`, `supervisorChoice`, `supervisorId`, `supervisor`) from the manager state, `status.json` and `factory-shutdown.ts`.
- **Compatibility.** An old `state.json` with `notes`, `parked[*].reported`, `startReported` or `reported` stays valid: the validator in `factory-state/state-file.ts` keeps them, and the manager ignores them. An old `status.json` with `holds`, `deliveredReportIds`, `lastDigestHash`, `unanswered` or `nextWakeAt` does not fail the start. Old supervisor Threads stay valid, and `thread list`, the history and the TUI show them.
- **Status.** `status.json` no longer has `supervisorThreadId`. The TUI and the CLI build and work without it. The TUI supervisor view can show the last old supervisor Thread or nothing. ROW-125 removes it.
- **Tests.** Daemon tests in `factory-manager.test.ts` with the faux worker provider and no supervisor provider:
  - Workers start without a supervisor session, and no Thread with the role `supervisor` is created.
  - Each `start` or `retry` decision gives one start. Two passes do not start the same work two times.
  - A `ConflictError` for one Story (for example a full host) does not stop the start of the other Stories.
  - A different error sets the attention entry `dispatch`.
  - `factory release` releases a parked Story, and the next pass starts it.
  - Change the other tests that use `start_worker` through a faux supervisor (`factory-manager.test.ts`, `remote-*.test.ts`, `worker-checks.test.ts`, `worker-executor.test.ts`, `messages.test.ts`, `factory-policy.test.ts` and others that `pnpm test` shows) so that the manager starts the workers.
- **Docs.** Update `docs/architecture/native-factory/` (README, controls, recovery, runtime and locks, Threads and history where they tell about the supervisor turn, tools, holds or notes), `docs/architecture/cli.md` for `factory release`, and `docs/architecture/storage.md` for `status.json` and `state.json`. Add `factory release` to `skills/rowbly-reference.md`, then copy it to each `skills/<name>/references/rowbly-reference.md`.

Not in scope:

- The removal of the supervisor settings (`factory.supervisorModel`), the CLI options `--supervisor` and `--supervisor-thinking`, `SUPERVISOR.md`, `rowbly prompt get supervisor`, the TUI supervisor view and the AI settings of the supervisor (ROW-125). They stay, but the factory does not use them.
- A TUI control for `factory release`.
- An action for stalled workers (`stalled` of the policy). No supervisor used `stop_worker`.
- A change to the workers or to their prompts.

## Technical notes

- Base the branch on the current `main`. It has ROW-120 (`stageClassOf` in `classifiedStages`), ROW-121 and ROW-122.
- `supervisor-loop.ts`: keep `runFactory`, the wake loop, `reconcilePolicy`, `refreshUpstreamAttention`, `removeStaleWorkerAttention`, `runSideSteps` and the network resume step. Replace `buildDigest`, `shouldSkipDigest`, `shouldRotateSupervisor`, `rotateSupervisor`, `deliverDigest`, `sendDigest` and `openSupervisor` with a dispatch step. Use the decisions that `reconcilePolicy` gives, or a new `scan` after the network resume, because the resume can change the decisions.
- `reserveWorker` already runs in `serial`, checks the eligibility again with `scan`, keeps the `requests` map and gives the prior Thread for a known request ID. The dispatch step must not call it inside `serial`, because `serial` does not nest.
- `createWorkerThread` uses `getState(manager).supervisorId` as `parentThreadId`. Remove the field; a worker Thread then has no parent.
- `promptHash` comes from `supervisor-digest.ts` and `manager-status.ts`, `worker-launch.ts` and tests use it. Move it next to `storyHash` in `src/services/factory-policy/factory-policy.ts` (or a small module that stays), with the same output, so that the stored prompt claims stay valid.
- `ReserveWorkerInput` keeps `model`, `host` and `resumeThreadId`, because `resumeWorker`, the control command `resume` and the tests use them. Update its comments that name the supervisor.
- New control type: `factory-control.ts` (`FactoryCommandType`, `COMMAND_TYPES`, validation of `storyId`), `commands/factory-runner/control-poller.ts` (`ControlTarget` and `executeCommand`), `factory-manager.ts` (a `releaseStory` method), `services/factory/factory.ts` (`releaseFactoryStory`), `commands/factory/factory.ts` (the subcommand, with `--json`). The release takes the state lock only, through `updateFactoryState`, inside `serial`.
- Do not load Pi in the release command path.
- Obey the lock order: never take the Project write lock while you hold the state lock.
- `factory-recovery.ts` must still close old supervisor Threads that a dead daemon left running.

## Assumptions

- `rowbly factory release` works only with a live daemon. Reason: the daemon writes `state.json` from its own scan, so a direct write while it runs can be lost; `resume` and `dismiss` already work only with a live daemon. This is the smallest scope.
- A `ConflictError` for one Story gives no attention entry. Reason: a full host or a paused provider is a normal condition, and the queue in `status.json` already shows the reason.
- No new attention entry for a parked Story. Reason: the queue in the status already shows the reason `parked`, and the `upstream-stuck:` entries already show a parked upstream Story.
- The model selection does not wait for ROW-123. Reason: ROW-123 is optional and is not an upstream Story of this Story. It adds the tag rule to `selectWorkerModel` later.
- The rename of `supervisor-loop.ts` and `supervisor-steps.ts` is optional in this Story. Reason: ROW-125 removes the word "supervisor" from `src/`. A developer can rename the files here, for example to `factory-loop.ts` and `loop-steps.ts`.
- The attempt flags `reported` and `startReported` and the parked flag `reported` can stay in the types for old files. Reason: the Story requires that an old `state.json` stays valid.

- (Development) The dispatch forgets a request ID whose Thread is final before it reserves. Reason: the policy counts the attempts of a Stage again after a budget reset (for example a Story that comes back from Done), so a new Stage stay can have the request ID of an earlier worker. Without this, the in-memory `requests` map would give the old Thread, and the Story would never start again in the same daemon. An active Thread keeps its request, so two passes still cannot start the same work two times.
- (Development) After a scan that gives the reason `stop confirmed this scan`, the loop runs one more pass at once. Reason: without a supervisor turn, the retry of a Story would wait for the 30-second timer.
- (Development) `pendingReports`, `markReported`, `PolicyReport`, `checkHistory` and `blockedItems` are removed, because only the digest used them. The files `supervisor-loop.ts` and `supervisor-steps.ts` keep their names; ROW-125 can rename them.
- (Development) The connectivity of the status still counts the provider of `factory.supervisorModel`, because ROW-125 removes that setting.
