## Goal

When a Story file changes, read only that Story again, and not the full board.

## Context

A change in a watched `.rowbly/` folder calls `data.refresh` in `src/tui/shell/shell/use-shell-data.ts`. This reads the full board again (`loadBoard`: `getProject`, `listStages`, `searchStories({})`, `getFactoryActivity`), parses the front matter of all Stories, and renders all of the board again. While the factory runs, agents write Story files frequently, so this occurs frequently. The watcher in `src/services/story-watch/story-watch.ts` already receives the name of the changed file, but `watchRoutes` in `src/services/project-watch/project-watch.ts` drops the name before it calls the callback.

## Scope

In scope:

- Send the changed file names from the watcher to the TUI, after the quiet time of `project-watch`.
- Add a service function that reads one Story by its file. A front end must not parse Story files.
- When only Story files changed, read each changed Story and put it into the board in memory. Remove a Story whose file was deleted.
- Read the full board again when a change has no file name, when a change is not a Story file (for example the project config, a Stage file, a Spec, a prompt, an attachment folder or a Stage folder), or when a read of one Story fails.
- Keep object identity for the Stories that did not change, so that memoised rows do not render again.
- Update the tests next to each changed service.

Not in scope:

- Changes to the factory daemon (`src/services/factory-manager/factory-loop.ts`) and to `thread-watch`. They keep their callbacks with no arguments.
- Partial reads for attachment, Spec, Stage or config changes. They continue to read the full board.
- A new watch of `state.json`. `useFactoryStateChanges` stays as it is.
- TUI tests (the repository rule is: no tests for the TUI).

## Acceptance criteria

- [ ] An edit of one Story file from a different process reads only that Story, and the board shows the change. A service test shows that the new single-Story read function returns the changed Story; a person can examine the TUI.
- [ ] A new Story file and a deleted Story file show correctly on the board (person check in the TUI; the service tests cover the read of a new file and the result for a missing file).
- [ ] A move of a Story to a different Stage (a new file in the new Stage folder and the removal of the old file) shows the Story only one time, in the new Stage.
- [ ] A change of the project config, a Stage file, a Spec, a prompt or an attachment still reads the full board again.
- [ ] A change with no file name still reads the full board again.
- [ ] The temporary file of an atomic write (`.<uuid>.tmp` in a Stage folder) alone does not cause a full read of the board.
- [ ] The Stories that did not change keep the same objects after the update. A unit test of the merge function in `src/services/story/story-order.ts` examines this with `toBe`.
- [ ] `project-watch.test.ts` shows that the callback of `watchRoutes` gets the list of changed names of one quiet time, as paths relative to `.rowbly/`, and `null` for an event with no name.
- [ ] The existing callers of `watchStories` and `watchRoutes` that use no argument still work, and their tests pass.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

Files that apply (paths relative to `packages/cli/`):

- `src/services/project-watch/project-watch.ts`: `watchRoutes`, `schedule`, `routeListener`. Collect the accepted names during the quiet time (`QUIET_MS`) and give them to `onChange` as one batch, for example `onChange(changes: readonly WatchChange[])`. Make each name relative to a common root (join the route path and the event name), or give the route path with the name, so that `stories/IN_DEVELOPMENT/ROW-01.md` and `stages/IN_DEVELOPMENT.md` are different. A name of `null` must stay in the batch (it means "read everything"). Clear the batch when the timer fires. Keep the type of the callback compatible with `() => void` callers.
- `src/services/story-watch/story-watch.ts`: `watchStories` passes the batch on. Add a pure service function that classifies a batch, for example `storyFileChanges(paths, changes)`, that gives either the list of Story file paths, or "full read". A Story file path is a file in `paths.storiesDir` or one of its Stage folders whose name agrees with `parseStoryFileName` (`src/services/story-files/story-files.ts`). Ignore a name that `writeFileAtomic` uses for its temporary file (`.<uuid>.tmp`, see `src/services/files/files.ts`). Each other name, and `null`, gives "full read". Test it in `story-watch.test.ts`.
- `src/services/story/story-read.ts`: add a function, for example `readStoryAt(path, ctx)`, that reads the config, reads one file with `readStoryFile`, checks it with `toStory`, and adds `attachmentCount` with `countAttachments`. It gives `undefined` when the file does not exist (`ENOENT`). It throws for an invalid Story. Export it from `src/services/story/story.ts` and test it in `story-read.test.ts`.
- `src/services/story/story-order.ts`: `withStory` puts a Story at the top of its Stage, because it is for a write of this process. A change from a different process can keep the old `updatedAt` (for example, a manual edit). Add a function that puts a Story at its place in board order: Stage order, then `updatedAt` with the most recent first, then number (the same order as `sortStoryFiles` and `searchStories`). Use `withPositions` so that unchanged Stories keep their references. Also add or use a removal by file `path` (not by ID), so that a Stage move that deletes the old file does not remove the new copy. Test it in `story-order.test.ts`.
- `src/tui/hooks/use-story-changes.ts`: pass the batch to the callback.
- `src/tui/shell/shell/use-shell-data.ts`: when the batch has only Story file paths, read each path with the new service function and apply the result to the current base board (put the Story, or remove the Story with that path when the result is `undefined`). Then read the factory activity again for the new Stories (`getFactoryActivity`), so that the activity agrees with the board. When the batch needs a full read, or when one read throws, call `data.refresh` as now. A possible method: keep the pending batch in a ref, and let the `useAsync` function of the board use the previous board and the batch, so that `refresh` keeps its race protection. The `local` board of a Story action is replaced by a new base, as now.
- Rules: services do not import `react` or `ink` (AGENTS.md rule 1). Use `.js` extensions in imports. Read `.agents/skills/rowbly-code-style/SKILL.md` before you write code.

## Assumptions

- The change keeps the callbacks of the factory daemon and of `thread-watch` with no arguments. Reason: the Story is about the reads of the TUI. This is the smallest scope.
- A Story is put at its place by `updatedAt` and number, not at the top of its Stage. Reason: a change from a different process can keep the old `updatedAt`. The board must have the same order as after a full read.
- A deleted file removes the Story with that `path`, not the Story with that ID. Reason: a Stage move writes the new file first and then removes the old file (`saveStoryFile`). A removal by ID can remove the new copy.
- The temporary file of an atomic write is ignored, and does not cause a full read. Reason: each Story write makes a `.<uuid>.tmp` file in the Stage folder. If it caused a full read, the change has no effect.
- After a partial update, the factory activity is read again for the new list of Stories. Reason: `withActivity` uses the identity of the list of Stories. Without a new read, the activity does not apply to the new board.
- Dependency data (`blocks`, `waitingFor`) is not a part of the board Stories, so a partial read does not need to update it. Reason: `searchStories` does not give these keys.
