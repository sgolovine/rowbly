Read the Spec `deterministic-factory` (decision 4).

## Goal

When a worker reports a problem, the manager shows it to the user as an attention entry. The supervisor does not read worker summaries to find problems. This removes one job of the supervisor before ROW-124 removes the supervisor session.

## Now

The worker tool `report_result` (`src/services/factory-worker/factory-worker.ts`, used by `src/services/factory-manager/local-executor.ts`) records `outcome`, `summary`, `blockers` and `problems`. Only the supervisor reads them, and it calls `raise_attention` (`supervisor-tools.ts`) when it thinks that a person must act. Examples from this Project: a flaky CI suite, a merge race, and a manual check of the TUI layout.

## Scope

In scope:

- When a worker Thread ends with the status `completed` and its reported result has one or more `blockers` or `problems`, the manager sets the attention entry `worker:<story-id>` with `storyId` set. The text has the Story ID, the Stage, the Thread ID, the outcome, and the first blockers and problems. The text is limited to 1000 characters (the limit of `raise_attention`).
- When a worker Thread ends with the status `failed`, the manager sets the same entry with the error message. A failure with the code `NETWORK` (connectivity) does not set it, because network resume handles it.
- A Thread that ends as `interrupted` or `cancelled` (factory stop or cancel) does not set or remove the entry.
- The manager removes the entry `worker:<story-id>` in these conditions:
  - A later worker Thread of the Story ends as `completed` with no blockers and no problems.
  - The Story is not in the Stage of its last worker Thread (the Story left the Stage). The supervisor pass examines this, near `refreshUpstreamAttention` in `supervisor-loop.ts`.
  - The Story does not exist (deleted). The same pass examines this.
- The same rules apply to a remote worker Thread. The remote executor (`src/services/remote-executor/remote-run.ts`) sends the same `completed` and `failed` events as the local executor, so the change in `worker-launch.ts` covers both.
- Tests of the manager, and the docs of the attention entries.

Not in scope:

- A change to the fields of `report_result`.
- New TUI views. The TUI shows the entry like all other attention entries.
- The removal of `raise_attention` or of the supervisor (ROW-124, ROW-125).

## Technical notes

- Put the pure rules in a new module `src/services/factory-manager/worker-attention.ts` with a test `worker-attention.test.ts`, like `upstream-attention.ts` and `outbox-attention.ts`. Export a key prefix constant (`WORKER_ATTENTION = "worker:"`), a function that builds the text from the Thread and the result or error, and a function that gives the entries to remove from the Stories and the last worker Threads.
- Set and remove the entry in `completeWorker` and `failWorker` in `src/services/factory-manager/worker-launch.ts`. Both run inside `serial(manager, …)`. Use `withEntry` and `withoutEntry` from `src/services/store/store.ts` with `setState`.
- `completeWorker` adds the problem "Story remains in the assigned Stage" when the Story did not move. Use only the result that the worker reported (`reported`) to decide, not this added problem. See Assumptions.
- `failWorker` gets the error class from `workerFailure` (`network-wait.ts`). Skip the entry when the code is `NETWORK_ERROR_CODE`. Skip when the factory is stopping (the Thread becomes `interrupted`).
- For the removal pass, `network-wait.ts` has `lastWorkerThreads` (the last worker Thread of each Story). Export it or a similar function, and use `listThreads` and `searchStories`.
- The manager persists attention in `status.json` (`manager-status.ts`) and loads it at start. No schema change: the entry uses the existing `{ text, storyId }` shape.
- Attention capacity: `raise_attention` refuses a new key when there are 100 entries. The manager entries in this Story do not use that check, like the other manager entries.
- Do not load Pi in the new module. It does no I/O.

## Assumptions

- The added problem "Story remains in the assigned Stage" from `completeWorker` does not make an entry by itself. Reason: the Story says "when a worker reports a problem", and this text is not from the worker. A worker that keeps the Story in its Stage on purpose (for example a `blocked` refinement) reports blockers, so it still makes an entry.
- A run that ends without a reported result (outcome `unknown`) and without a failure does not make an entry. Reason: smallest scope; the worker reported no blockers or problems, and the supervisor still sees these Threads until ROW-124.
- The text limit is 1000 characters, the same as `raise_attention`. The text has a maximum of the first 3 blockers and the first 3 problems. Reason: the Story says "in the limits of the other attention entries", and the TUI shows a maximum of 12 entries.
- A dismissed `worker:` entry comes back only when a new Thread of the Story ends with blockers, problems or a failure. Reason: the entry is set by an event, not by each pass, so a dismiss stays.
