## Goal

Make the TUI start faster. The profile of ROW-137 found a hot spot in the import of the TUI modules at launch. When the TUI loads less code before the first render, the user sees the board sooner.

## Hot spot

- Function: `loadInProductionMode` (`src/services/react-mode/react-mode.ts`). `src/cli-main.ts` calls it for `import("./tui/index.js")`.
- Inclusive CPU time: 138 ms on the main thread (median run). The top-level evaluation of `cli-main` is 232 ms inclusive and holds this time.
- Most of the time is module compile and load (`compileSourceTextModule`, `ModuleWrap`, `realpathSync`) for the TUI bundle (about 540 KB), Ink, React and Yoga.
- Scenario: the production-mode 12 s board session of ROW-137. 138 Stories, 140x38, Node 24, `NODE_ENV` not set.
- The measured launch time to the first Story row is 1.28 s.

## Scope

In scope:

1. Load the screens that the board does not show at launch with a dynamic `import()`, so that tsup puts them in separate chunks:
   - The Settings Modal (`SettingsModal`, `src/tui/screens/settings/`, about 205 KB of source).
   - The Factory Modal and the Checks Modal (`FactoryModal`, `ChecksModal`, `src/tui/screens/factory/`).
   - The onboarding screen (`Onboarding`, `src/tui/screens/onboarding/`).
2. Keep the small helpers that the board shows at launch in the main TUI chunk. The header, the Factory button, the Checks button and the shell keys use `checksCount`, `liveChecks`, `connectivityWord`, `factoryProblems` and `factoryState`. Import them directly from `screens/factory/check-jobs.ts` and `screens/factory/factory-status.ts`, not from the `screens/factory/index.ts` barrel. A module that the main chunk imports statically and that a lazy screen also imports stays in the shared code. Thus, the barrel import must not pull the modals into the main chunk.
3. Make sure that the Node compile cache also applies to the TUI chunk and to the new lazy chunks. The compile cache is already on (`src/cli.ts`, `src/services/compile-cache/`, commit `da342ea5`). No code change is expected for this item. Only examine it and record the result.
4. Measure the launch again and record the result (see the acceptance criteria).

Not in scope:

- The Story modal, the Story list, the Threads view (`src/tui/screens/threads/`) and the Stage form. The board or the Story panel uses them, or they are small.
- The Pi SDK load in the worker thread (`loadPi`, `createFactoryRuntime`). ROW-140 has this work.
- Changes to the tsup chunk settings or to minification. tsup already splits each dynamic `import()` into its own chunk (`docs/architecture/tooling.md`).
- Changes to the bundles of Ink, React or Yoga.

## Technical notes

- Entry: `src/cli.ts` turns on the compile cache, then imports `src/cli-main.ts`. `src/cli-main.ts` loads `src/tui/index.tsx` with `loadInProductionMode(() => import("./tui/index.js"))`. Do not change this order. `src/cli.test.ts` examines it.
- Lazy load: use `React.lazy` with a `Suspense` boundary, or a dynamic `import()` in a hook that keeps the loaded component. Ink 8 and React 19 support `Suspense`. Put the boundary at the place that renders the screen:
  - `src/tui/shell/shell-overlays/shell-overlays.tsx` for `SettingsModal`, `FactoryModal` and `ChecksModal`.
  - `src/tui/shell/story-panel/story-panel.tsx` for `Onboarding`.
- `React.lazy` needs a default export. Use `lazy(() => import("...").then((m) => ({ default: m.SettingsModal })))`, so that the screen modules keep named exports.
- Static importers of `screens/factory/index.js` outside the screen: `src/tui/shell/checks-button/checks-button.tsx`, `src/tui/shell/shell/shell-keys.ts`, `src/tui/shell/header/header.tsx`, `src/tui/shell/factory-button/factory-button.tsx`. `check-jobs.ts` imports `../stories/thread-text.js`. That module is already in the main chunk.
- Find other static importers before the change: `grep -rn "screens/\(settings\|factory\|onboarding\)" src/tui`. Each import from inside the same screen folder is permitted.
- Keep the import boundary of the CLI: `src/commands/tui-boundary.test.ts` and `src/cli.test.ts` must pass.
- Obey the `rowbly-code-style` and `rowbly-tui-design` skills. Use `.js` extensions in relative imports.
- Do not write Vitest tests for the TUI (AGENTS.md rule 4). The checks of the chunks are build-output checks.
- Measurement method: the `## Performance` section of `docs/architecture/tui.md` on the branch `story/ROW-137` (commit `87b3d603`). Run steps 1 to 11 and summarize the `.cpuprofile` files as that section tells you.
- The method sets `HOME` to an empty temporary folder. The compile cache is then in `$HOME/.cache/rowbly/compile-cache`, if `XDG_CACHE_HOME` is not set. Thus, the first run has a cold cache. For the warm cache, run the TUI one time with the same `HOME` before the measured runs.
- Update `CHANGELOG.md` if the repository has an entry for each Story.

## Assumptions

- The compile cache item of `## Ideas` is complete. Reason: commit `da342ea5` (`perf(cli): turn on the Node compile cache at startup`) is in the history, and `src/cli.ts` turns on the cache before it imports `cli-main`. The dynamic import of the TUI occurs after that, so the cache applies to it. This Story only examines it and measures a warm and a cold cache.
- The ROW-137 profile possibly used a cold compile cache. Reason: the method uses an empty `HOME`, and the cache is in the cache folder of `HOME`. Thus, the 138 ms possibly includes compile time that a warm cache removes. The new measurement records both cases.
- The lazy screens are Settings, the Factory Modal, the Checks Modal and onboarding. Reason: the author named Settings, the Factory view and onboarding. The Factory view in the code is the Factory Modal and the Checks Modal (`screens/factory/`). The Threads view (`screens/threads/FactoryView`) shows in the Story panel, so it stays in the main chunk.
- The `## Performance` section of `docs/architecture/tui.md` is on the branch `story/ROW-137`, and is not yet in `main` at refinement time. Reason: `git merge-base` shows that commit `87b3d603` is not in the base of this worktree. If ROW-137 is merged before development, update that section. If it is not merged, add a short `## Performance` note for ROW-139 with the new numbers, and refer to the method of ROW-137.
- The acceptance criterion for speed is "not slower than 1.28 s", not a fixed gain. Reason: the gain depends on the hardware and the cache state. The Story does not give a target number.
- A short empty frame while a lazy screen loads is acceptable. Reason: the import of a local chunk takes a few milliseconds. A permanent loading screen is not necessary.
- No measurement was done during refinement. Reason: the worktree has no `node_modules`, so `pnpm build` did not run.
