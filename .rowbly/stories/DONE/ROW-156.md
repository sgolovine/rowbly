## Goal

Make each keypress in the TUI do less React work, so that the TUI shows each keypress quickly on a large board. The user sees the same keys, focus and mouse behaviour, but a cursor move renders fewer components.

## Context

At refinement time (2026-11-18), 6 files in `src/tui/` use `memo`: `Sidebar`, `Footer`, `StoryPanel`, `StorySidebar`, `Header` and `ShellOverlays`. The board state is near the top of the tree, in `use-shell` and `use-shell-data`. Thus a cursor move renders `StoryList` again, and `StoryList` renders each visible `StoryListItem` and `StoryRow` again. `StoryList` shows only the rows in its window (`listWindow`), so the cost grows with the height of the terminal, not with the number of Stories.

Ink sends each keypress to each active `useInput` handler. The TUI has 48 `useInput` calls (the first text of this Story said 96). Each call already sets `isActive`.

## Scope

In scope:

- Measure first, on the same large board before and after the change:
  - The CPU profile with the method of `docs/architecture/tui.md` → "Performance" → "Method" (`--cpu-prof`, steps 1 to 11, production mode).
  - The render counts of `StoryList`, `StoryListItem`, `StoryRow`, `SidebarRow` and `SidebarItem` for one `Down` key in the Story list. Use a temporary React `<Profiler>` or a temporary render counter in a development build (`NODE_ENV=development`). Do not commit the counter.
- Memoise the rows that the board shows many times: `StoryRow` (`src/tui/screens/stories/story-row/`), `StoryListItem` (`src/tui/screens/stories/story-list-item/`), `SidebarRow` (`src/tui/components/sidebar-row/`) and `DropSlotRow` when it is cheap to do.
- Make the props of these rows stable across a cursor move, so that `memo` has an effect. See "Technical notes".
- Audit the 48 `useInput` calls. Make sure that each handler of a hidden screen, a covered layer or an inactive pane has `isActive: false`. Repair each handler that does not.
- Examine `concurrent: true` in the Ink `render()` options in `src/tui/terminal.ts`. Turn it on only if the measurement shows a benefit and all checks pass. If it is on, use `useDeferredValue` or `useTransition` for slow output only (for example fuzzy search results and the Markdown detail view).
- Add the results to the "Performance" section of `docs/architecture/tui.md` in a new subsection "Keypress render work (ROW-156)", in STE.

Not in scope:

- Changes to `src/services/` or to the storage format.
- Changes to the keys, the focus, the mouse behaviour or the look of the TUI.
- A new virtualisation of the Story list. The list already shows only the rows in its window.
- New TUI tests (the repository rules forbid TUI tests). Pure helpers that move out of a component can get a unit test, as in `src/tui/shell/shell/*.test.ts`.

## Technical notes

- Read `.agents/skills/rowbly-code-style/SKILL.md` and `.agents/skills/rowbly-tui-design/SKILL.md` first. Rule 4 of "React components" forbids `useCallback` or `useMemo` only to satisfy a lint rule. Memoisation for performance is permitted. Do not put `env` or `actions` in a dependency array.
- Use the existing pattern: `export const X = memo(function X(...) { ... })`, as in `src/tui/components/sidebar/sidebar.tsx` and `src/tui/shell/story-panel/story-panel.tsx`.
- Props of `StoryListItem` that change on each render of `StoryList` today, and so make `memo` useless:
  - `onClick={(event) => clickRow(env, item.index, event)}`: a new function each render.
  - `dragProps={rowDragProps(env, item.row, item.index)}`: a new object each render.
  - `tagLabels={tagLabels(row.story.tags, tags)}` in `StoryListItem`: a new array each render.
  - `env` in `StoryList` is a new object each render.
- A possible solution: keep the latest `env` in a ref with `useLatest` from `src/tui/hooks/refs.ts`, and give each row a stable callback object plus its `index`. The row makes its own handlers from the ref. Another solution: a custom `arePropsEqual` for `memo` that compares the data props and ignores the function props, if the functions always read the latest `env` through a ref. Select one solution and use it for both `StoryListItem` and `SidebarRow`. `SidebarRow` gets `env` (`SidebarRowEnv`) from `Sidebar` as a new object each render.
- `rows` comes from a `useMemo` in `src/tui/shell/shell/use-shell.ts`, and each `StoryListRow` keeps its identity while the board does not change. Keep this.
- `activity[id]` and `hostLost` are data props. Make sure that their values keep the same identity on a cursor move.
- The Ink options are in `runFullScreen` in `src/tui/terminal.ts`. Ink 8.0.0 has `concurrent?: boolean` (default false) in its `RenderOptions`. Concurrent mode changes the timing of renders.
- The worktree has no `node_modules`. Run `pnpm install` before the checks.
- The Pi SDK stays behind the lazy boundary in `src/services/pi-runtime/`. `src/commands/tui-boundary.test.ts` checks the TUI imports.

## Assumptions

- The "large board" is a copy of this Project (about 140 Stories at refinement time) in a 140x38 terminal, as in the existing "Performance" section. Reason: this keeps the new values comparable with the earlier runs.
- The render counts come from a temporary counter or `<Profiler>` in a development build, and the counter is not committed. Reason: production React does not call `<Profiler>` callbacks, and the repository has no TUI tests.
- "The panels" of the first text means the panels that the shell already memoises (`StoryPanel`, `StorySidebar`, `Sidebar`). No new panel memo is necessary unless the measurement shows a panel that renders on a cursor move without a change. Reason: smallest scope that agrees with the intent.
- Concurrent mode stays off unless the measurement shows a clear decrease in the keypress-to-frame time and all checks pass with no new `act()` work. Reason: the smallest scope, and concurrent mode can change the order of renders that the mouse registry and the tests expect.
- The criterion "a cursor move does not render the rows that did not change" means a maximum of 2 changed rows when the window does not scroll. When the window scrolls, all visible rows can render. Reason: a scroll changes which rows show.
- The measurements go into the Story description and also into `docs/architecture/tui.md`. Reason: the "Performance" section of the docs is the place of earlier profile results.
## Measurements

Run of 2026-11-17 on a copy of this Project: 157 Stories, a 140x38 terminal, Node 24.22.1, Linux x86_64 (16 cores, Intel i9-10885H). Other factory workers ran at the same time (load average 1.2 to 13). The base build (`fadab551`) and the ROW-156 build alternated. Each CPU value is the median of 6 production runs (`--cpu-prof`, steps 1 to 11 of `docs/architecture/tui.md` → "Performance" → "Method").

| Measurement | Base build | ROW-156 build |
| --- | --- | --- |
| CPU busy in the session (`NODE_ENV=production`) | 2.16 s | 1.76 s |
| React inclusive time in the session | 1,183 ms | 924 ms |
| CPU busy in the window of the 10 arrow keys (step 7) | 432 ms | 340 ms |
| React render phase in the window of the 10 arrow keys | 37 ms | 15 ms |
| Renders of `StoryList` for one `Down` key in the list | 1 | 1 |
| Renders of `StoryListItem` for one `Down` key in the list | 31 | 2 |
| Renders of `StoryRow` for one `Down` key in the list | 25 | 1 or 2 |
| Renders of `SidebarRow` for one `Down` key in the Stage sidebar | 7 | 2 |
| Renders of `SidebarItem` for one `Down` key in the Stage sidebar | 7 | 2 |

- The render counts come from a temporary counter (one line in a file for each render) in a development build (`NODE_ENV=development`). The list window did not scroll. The counter is not committed.
- `StoryRow` renders 1 time when the cursor moves between a Stage heading and a Story, because a heading row is a `SectionHeadingRow`.
- Most of the CPU time of a key is in the commit phase (Ink output, Yoga layout, terminal write). Memoised rows do not decrease this time.

## Key handler audit

All 48 `useInput` calls in `src/tui/` have an `isActive` value. The values come from `useIsActive()` (the shell, the `OverlayHost` and each `Modal` set `ActiveContext` to false for a covered layer), from `useCovered()` (a task Modal over the content), or from a focus prop of the parent pane.

Changed handler:

- `ScrollBody` of `SectionNav` (`src/tui/screens/settings/section-nav/section-nav.tsx`): it took `Page Up` and `Page Down` also when the Settings section had the focus. Now `active` is `focused`, and `wheel` is `clickable`, so the mouse wheel does not change.

No other handler changed.

## Concurrent mode decision

Concurrent mode stays off. With `concurrent: true` in `runFullScreen`, the median of 3 alternated runs was: CPU busy 1.58 s (off: 1.49 s), CPU busy of the key window 270 ms (off: 269 ms), React render phase of the key window 12 ms (off: 13 ms). The measurement shows no benefit, and concurrent mode changes the timing of the renders. Thus no `useDeferredValue` or `useTransition` was added.

## Development notes

- The rows read the latest environment of the list or of the sidebar through a ref (`useLatest`). Each row gets the ref, its index and its data props, and makes its handlers from the ref. `StoryListItem`, `StoryRow` and `SidebarRow` use `memo`.
- `StoryList` gives one shared empty tag list, because `projectTags` gives a new empty array for a Project with no tags.
- `DropSlotRow` is not memoised. It shows only during a drag, and only one shows.
- Behaviour check: a scripted `agentic-tui` session (keys `↓`/`↑`, clicks, `shift+click`, drag and drop, `space` marks, `shift+↑/↓`, click on the selected row, Stage sidebar clicks) gave the same screen text for the base build and the ROW-156 build in all 16 steps.
- No new unit test: `docs/architecture/testing.md` says "Do not put a test in `src/tui/`", and the change has no new pure helper.
- `pnpm test` fails in the factory worker environment because `TSX_TSCONFIG_PATH=packages/cli/tsconfig.json` is inherited from the factory process (37 tests fail in the same way on the base branch). With `env -u TSX_TSCONFIG_PATH pnpm test`, all tests pass.
