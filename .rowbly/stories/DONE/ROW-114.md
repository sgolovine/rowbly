## Goal

When the same Story is in two Stage folders, Rowbly keeps one copy and removes the other copies. On 2026-11-16, `stories/DONE/ROW-78.md` and `stories/IN_REVIEW/ROW-78.md` were two copies of the same Story. Only `stage` and `updatedAt` were different. The TUI list then showed the Story many times, kept old text on the screen and could not scroll past it. The ROW-81 repair did not help, because the two copies had factory state (the same `worktree` and `pull_request`), and a re-number is not the correct repair for a copy.

Result: two or more Story files with the same Story ID and the same `uid` are copies. Rowbly keeps the copy with the newest `updatedAt` and removes the other copies. It tells the user about each removed copy.

## Scope

In scope:

- The duplicate check finds copies: files with the same Story number and the same `uid`.
- Copies that are different only in `stage`, `position` and `updatedAt`: keep the copy with the newest `updatedAt` and remove the others. If the `updatedAt` values are equal, keep the copy with the newest modification time, then the first path in string order.
- Copies that are different in other frontmatter keys or in the body: do not change a file. Report the copies as not repaired, with the paths, so that the user can merge them.
- The repair runs in `rowbly doctor --fix` and in the TUI board load, at the same place as the ROW-81 re-number repair, and before it.
- A TUI info toast and a `doctor` line for each removed copy, for example `ROW-78: removed the old copy in DONE`.
- Update `docs/architecture/storage.md` (the Story folder doctor table).

Not in scope:

- Files without `uid`. They stay with the ROW-81 rules.
- Files with the same number and a different `uid`. See ROW-115 ("Re-number a duplicate Story ID with its references").
- A search for the process that wrote the second copy.

## Technical notes

- The `uid` of ROW-112 is on `origin/main` (merge commit `97ab56fb`). The worktree HEAD does not have it. Merge `origin/main` into the branch before the work starts. `Story.uid` is in `src/services/story/story-types.ts`. Read the `uid` from the frontmatter of each file in the plan.
- Compare the copies by their parsed frontmatter without `stage`, `position` and `updatedAt`, and by the body text. Each other difference makes the group not repaired.
- `src/services/story-renumber/duplicate-plan.ts` `planDuplicates()` finds the groups of the same number. Add the copy groups before `decideGroup()`.
- `src/services/story-renumber/story-renumber.ts` applies the plan. `src/services/doctor/duplicate-checks.ts` and `src/tui/shell/shell/use-shell-data.ts` `repairDuplicates()` call it.
- Use the same safety steps as the re-number: read the bytes in the plan, read them again before the remove, and stop if they changed. Take no lock, as the ROW-81 repair does.
- `removeStoryFile()` in `src/services/story-files/story-folders.ts` removes a file and its empty Stage folder.

## Assumptions

- The newest `updatedAt` is the correct copy. Reason: the last write of the Story is the newest state of the Story. Each Stage move sets `updatedAt`.
- Copies with different content need a person. Reason: a remove would lose an edit.
- A copy group goes out of the input of `decideGroup()`. If a number group also has a file with a different `uid` or no `uid`, the copies are removed first and the files that stay go to the ROW-81 rules. Reason: the smallest change that agrees with "before the re-number".
- The doctor issue of a copy group is an `error`, the same as a duplicate Story ID. Reason: the same severity as the ROW-81 check for the same symptom.
