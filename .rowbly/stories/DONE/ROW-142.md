## Goal

Make the factory start faster. Now `rowbly factory start` fails with "Factory readiness timed out", but the daemon starts and becomes ready after approximately 60 s. The start waits only 15 s (`waitForReady` in `src/services/factory/factory.ts`). Most of the start time is the recovery of the Threads.

The user gets a factory start where one recovery writes `state.json` a maximum of one time, and the recovery time does not increase with one locked full-file write for each Thread.

## Problem

- `recoverFactory` (`src/services/factory-recovery/factory-recovery.ts`) calls `recoverThread` for each Thread in `.rowbly/runtime/threads/`. Each call does `assertFactoryOwnership`, and then `projectNativeAttempt` (`src/services/thread/thread-projection.ts`).
- `projectNativeAttempt` calls `updateFactoryState` one time for each Thread. Each call takes the state lock, reads and parses `.rowbly/state.json`, and writes the full file again with `durable: true`. It writes the file also when the attempt did not change.
- Measured on this Project: 689 Threads, `state.json` is 1.2 MB with 664 attempts. One update with no change takes approximately 26 ms. 689 updates take approximately 18 s for each recovery.
- The start recovers two times (`recover()` in `src/commands/factory-runner/factory-runner.ts` and `recoverAndConfigure` in `src/services/factory-manager/factory-manager.ts`). Thus the recovery takes approximately 36 s. A different Story can remove the second recovery.
- The time increases with each new Thread.

## Scope

In scope:

1. Project the attempts of all Threads in one `updateFactoryState` call (or one `withStateLock` transaction) during recovery. Read each Thread one time. Do not take the state lock one time for each Thread.
2. Write `state.json` only when the projection changes an attempt. Keep the attempts that do not change as they are.
3. Keep the order and the result of the recovery the same: interrupt the Threads of a dead owner first, as now, and then project the attempts. A Thread on a worker host keeps its status.
4. Keep the ownership check. One check before the batch write, under the state lock, is sufficient. Do not take the Project write lock while you hold the state lock.
5. The batch write must be safe to do again after a crash, as the current projection is.

Not in scope:

- The second call of `recoverFactory` during a start.
- A change to the 15 s wait limit of `waitForReady`.
- Removal or archive of old Threads or old attempts.
- The speed of the first factory pass after recovery.
- A change to the write behaviour of `projectNativeAttempt` for its other callers (`factory-manager/worker-reservation.ts`, `factory-manager/manager-state.ts`).

## Acceptance criteria

- [ ] One recovery of a Project with many Threads (a test uses at least 20 worker Threads) writes `state.json` not more than one time. A test examines the count of writes, for example with a spy on `writeState` or with the `mtime`/`updatedAt` of `state.json`.
- [ ] A recovery with no changed attempts does not write `state.json`. A test runs `recoverFactory` two times and examines that the second run does not write the file (`updatedAt` does not change).
- [ ] The existing tests of `factory-recovery` and `thread-projection` pass with no change to the expected attempts.
- [ ] A new test recovers a mix of Threads: a local active worker of a dead owner (becomes `interrupted`), a completed worker, a remote worker on a worker host (keeps `pending`/`running`), and a non-worker Thread (no attempt). The test examines each attempt and the attempt count (no duplicates).
- [ ] `projectNativeAttempt(id, ctx)` for one Thread gives the same attempts as before for the other callers. The `thread-projection` tests examine this.
- [ ] If the owner token in `factory.lock` changes before the batch write, recovery throws `ConflictError` ("Factory owner token changed") and does not write `state.json`. A test examines this.
- [ ] Manual check (a person, on the canonical Project): the time from the owner lock to the `starting` event in `.rowbly/runtime/logs/<token>.jsonl` is less than 10 s. Record the time before and after the change in the PR.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

- `src/services/thread/thread-projection.ts`: `projectedState(id, state, ctx)` reads the Thread with `getThread` and replaces or appends one attempt. Split it into a pure function that takes a `ThreadRecord` and a `PolicyState` and gives the new `PolicyState`. Keep `projectNativeAttempt(id, ctx)` as a wrapper for the other callers. Add an export, for example `projectNativeAttempts(threads, ctx, options)`, that applies the pure function to all Threads in one state transaction.
- Find the existing attempt by `threadId`. In the batch, build a `Map` from `threadId` to the attempt index, so that the batch is O(n) and not O(n²) for 689 Threads.
- To compare an attempt, compare the projected attempt to the existing attempt field by field (or with a stable JSON compare). An attempt is changed only if a field value is different. `projectedAttempt` sets `model: undefined` when the Thread has no model; treat a missing key and an `undefined` value as equal.
- `src/services/factory-state/factory-state.ts`: `updateFactoryState` always calls `writeState`, and `writeState` sets `updatedAt`. To skip the write, use `withStateLock` + `readState` and call `writeState` only when an attempt changed. Do not change `updateFactoryState` for its other callers. Do not compare the full state, because `updatedAt` always changes.
- `src/services/factory-recovery/factory-recovery.ts`: `transitionThread` (used by `interruptThread`) takes the state lock itself (`thread-change.ts`). The state lock is not re-entrant. Thus do all interrupts first, outside the batch transaction, then read the current Threads again (or re-read only the interrupted Threads), then run the batch projection.
- Ownership: keep `assertFactoryOwnership` before each interrupt (interrupts are few), and call it one time inside the state lock before the batch write. `assertFactoryOwnership` reads only `runtime/factory.lock`. It does not take the Project write lock, so it is safe under the state lock.
- Crash safety: the batch is one atomic `writeState` (temporary file and `rename`). A crash before the rename leaves the old file; the next recovery projects again. The projection is idempotent: it replaces an attempt by `threadId` and never appends a duplicate.
- Keep the projection code free of Git, model and `projectWrite` calls inside the state lock (see the comment on `updateFactoryState`).
- Docs: update `docs/architecture/native-factory/recovery.md` ("Recovery after owner death") to say that recovery repairs all projections in one state write, and writes nothing when no attempt changed. Use STE.
- Tests: `src/services/factory-recovery/factory-recovery.test.ts` and `src/services/thread/thread-projection.test.ts`. Use `useTestProject`. Remote Threads need a `host` other than `local`.

## Assumptions

- The automated test for the write count uses a small Project (at least 20 Threads), not 689 Threads and a 1.2 MB file. Reason: the count of writes does not depend on the size, and a large fixture makes the test suite slow. The 689-Thread timing is a manual check on this Project.
- `projectNativeAttempt` for one Thread keeps its current behaviour, which writes also when nothing changed. Reason: the Story asks for no change for the other callers; the smallest scope is to change only the recovery path.
- Recovery reads the Thread list again after the interrupts, or re-reads only the interrupted Threads. Reason: `listThreads` gives the records before the interrupt, and the projection must use the new status. "Read each Thread one time" applies to the projection step.
- The ownership check before each interrupt stays. Reason: it protects the Thread writes, and interrupts are few, so it does not add measurable time.
