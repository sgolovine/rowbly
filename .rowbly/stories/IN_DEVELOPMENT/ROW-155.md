## Goal

Four form modals repeat the same save and close code. Each has an `XFormEnv` interface, calls `useToast`, and has a save function that ends with `showToast(toast, "info", existing ? "Updated …" : "Added/Created …")` and `onSaved(saved)`. Each renders a `FormModal` with the title `existing ? "Edit X › …" : "New X"`.

Move this shared code into one generic component, `EntityFormModal<T>`. The fields, the initial values and the service call are different, and they stay in each modal. The user sees no change: the titles, the fields, the toasts and the behaviour stay the same. The expected saving is about 40 lines.

## Scope

In scope:

- A new library component `EntityFormModal<T>` in `src/tui/components/entity-form-modal/`.
- Change these four modals to use it:
  - `src/tui/screens/settings/custom-field-form-modal/custom-field-form-modal.tsx`
  - `src/tui/screens/settings/tag-form-modal/tag-form-modal.tsx`
  - `src/tui/screens/settings/prompt-form-modal/prompt-form-modal.tsx`
  - `src/tui/screens/stages/stage-form-modal/stage-form-modal.tsx`
- A row for `EntityFormModal` in the component table of `.agents/skills/rowbly-tui-design/SKILL.md`.

Not in scope:

- Other users of `FormModal` (hosts, git, project, display, AI and check sections, spec dialogs, attachments tab).
- A change to `FormModal`, `Form`, the services or the public props of the four modals.
- A change to the callers of the four modals (`shell-overlays.tsx`, `custom-fields-section.tsx`, `prompts-section.tsx`, `tags-section.tsx`, `stages-section.tsx`).
- Delete support (`onDelete`) in `EntityFormModal`.

## Technical notes

- Proposed props:

  ```ts
  interface EntityFormModalProps<T> {
    /** The name of the record kind in the title, for example `Custom Field`. */
    noun: string;
    /** The record to edit. Without it, the form creates a record. */
    existing?: T;
    /** The part of the edit title after `›`, for example the label or the tag value. */
    titleOf(existing: T): string;
    fields: readonly FormField[];
    initialValues: FormValues;
    /** Calls the service. May throw a `ValidationError`. */
    save(values: FormValues, existing: T | undefined): Promise<T>;
    /** The name of the saved record in the toast. */
    labelOf(saved: T): string;
    /** The verb of the toast when the form creates a record. Default `Added`. */
    verb?: string;
    onSaved(saved: T): void;
    onClose(): void;
  }
  ```

- Title: `existing ? \`Edit ${noun} › ${titleOf(existing)}\` : \`New ${noun}\``.
- Toast: `existing ? \`Updated ${labelOf(saved)}\` : \`${verb ?? "Added"} ${labelOf(saved)}\``.
- The Prompt modal always edits: it passes `existing={prompt}` and `labelOf={(p) => \`the ${p.label} prompt\`}`, so its toast stays `Updated the <label> prompt`.
- The Stage modal passes `verb="Created"`.
- The Tag modal computes its `fields` and `initialValues` from `tag` (edit has only the `Label` field) and passes `titleOf={(t) => t.value}`.
- The Custom Field modal keeps `parseOptions` and its input mapping in its own `save` function.
- Follow the `rowbly-code-style` skill: put the save logic in a top-level function with an `env` object as the first parameter (for example `submitEntity(env, values)`), and keep the JSX handler one expression.
- Follow the `rowbly-tui-design` skill. Library components can import from `../../hooks/index.js` (`FormModal` already does).
- Use `.js` extensions in relative imports. Use dash-case names for the new folder and files.
- Do not write TUI tests (AGENTS.md rule 4).

## Assumptions

- The Prompt modal uses `labelOf` to make the text `the <label> prompt`, and it does not get a separate toast option. Reason: this keeps the proposed prop list of the author and keeps the toast text unchanged.
- `save` gets `existing` as its second parameter. Reason: the Custom Field, Tag and Stage services need the key or value of the edited record, and this keeps each modal free of an extra closure over its props.
- `EntityFormModal` goes in the component library (`src/tui/components/`), not in `src/tui/screens/settings/`. Reason: the Stage modal is in `src/tui/screens/stages/`, so the component is shared across screens.
- `onDelete`, `submitOnEnter`, `children` and `extraHints` are not props of `EntityFormModal`. Reason: none of the four modals uses them; the smallest scope is enough.
- The user-visible behaviour does not change, so `docs/architecture/tui.md` does not change. Reason: the documentation names `TagFormModal`, which stays.
