## Goal

The records that belong to a Story keep the Story `uid` (added by ROW-112), so that Rowbly can find the correct Story when its number changes or when two Story files have the same number. Today these records keep only the Story ID:

- the factory attempts in `.rowbly/state.json` (`story`)
- the Threads in `.rowbly/runtime/threads/` (`storyId`)
- the outbox entries of a remote worker host (`storyId`)
- the attachment records in `.rowbly/attachments/<ID>/manifest.json`

Result: each new record of these kinds also has `storyUid`. A read finds the Story by `storyUid` when it has one, and by the Story ID when it does not.

## Scope

In scope:

- A new attempt, a new worker Thread, a new outbox entry and a new attachment record get `storyUid` from the Story. If the Story has no `uid`, the record has no `storyUid` key.
- One shared resolver in the Story service, for example `resolveStoryRef({ id, uid }, ctx)` or a pure `matchStoryRef(stories, { id, uid })`. It gives the Story with this `uid` first. If no Story has this `uid`, or the record has no `storyUid`, it gives the Story with the ID, as today.
- These reads use the resolver (or the same match rule):
  - `findStory` in `src/services/outbox-apply/apply-state.ts` (the apply of field and attachment entries).
  - The match of attempts to a Story in `src/services/factory-policy/factory-policy.ts` and `policy-records.ts` (`attempt.story === story.id` and similar).
  - The Story filter of `listThreads` in `src/services/thread/thread-list.ts`.
- Old records without `storyUid` stay valid. Rowbly does not rewrite them.
- Validation accepts a record with or without `storyUid`. A `storyUid` that is present must be a string.
- Update `docs/architecture/native-factory/` (attempts, Threads, outbox) and `docs/architecture/storage.md` (attachment manifest) for the new key.

Not in scope:

- `dependsOn` lists of Stories and the Story links of Specs. They stay Story IDs.
- A re-number of Stories, and the repair of duplicate Story IDs (ROW-115).
- A migration that adds `storyUid` to old records.
- A change to the attachment folder name. It stays `.rowbly/attachments/<ID>/`.
- Other ID comparisons (for example in `manager-status.ts`, `supervisor-loop.ts`, `story-renumber/`, `check-queue/`). They stay as they are.
- A `storyUid` in the TUI or in the CLI text output. `--json` output can include it.

## Acceptance criteria

- [ ] A service test for each record kind (attempt, worker Thread, outbox entry, attachment record): a new record has the `storyUid` of its Story.
- [ ] A service test of the resolver: a reference with a `storyUid` finds its Story after the Story file gets a new number (a different ID).
- [ ] A service test of the resolver: a reference without `storyUid`, or with a `storyUid` that no Story has, finds its Story by the Story ID.
- [ ] A service test of the outbox apply: an entry without `storyUid` (from an older remote build) applies as today.
- [ ] A service test: a Story without `uid` gives records without `storyUid`, and no error occurs.
- [ ] A service test: `state.json` with attempts without `storyUid` loads, and an attempt with a `storyUid` that is not a string is invalid.
- [ ] The board, help, doctor, status and history paths do not load Pi (the existing lazy-boundary tests pass).

## Technical notes

- ROW-112 is merged to `origin/main` (commit `97ab56fb`). `Story.uid?: string` is in `src/services/story/story-types.ts`, and `story-read.ts` reads it. If the worktree base does not contain this commit, start the branch from `origin/main`.
- Attempts: `src/services/factory-state/state-file.ts` validates an attempt (`validAttempt`: `story`, `stage`, `workerId`). The type is `PolicyAttempt` in `src/services/factory-policy/factory-policy.ts`. New attempts are made in `factory-policy.ts` (decisions with `story: story.id`) and `src/services/factory-manager/worker-launch.ts` (`story: story.id`). `src/services/factory-recovery/` reads them.
- Threads: `src/services/thread/thread-types.ts` (`storyId?`), `thread-change.ts`, `thread-validate.ts`, `thread-list.ts`, `thread-groups.ts` and `thread-projection.ts`. The worker launch in `worker-launch.ts` has the Story and can give its `uid` to the Thread.
- Outbox: `src/services/outbox/outbox.ts` (entry types with `storyId`) and `outbox-file.ts` write the entries. `src/services/attachment/attachment.ts` calls `recordAttachmentAdd` with `storyId: story.id`. `src/services/outbox-apply/` applies them on the main machine (`outbox-shape.ts` validates the shape). A remote worker host can run an older build, so the apply must accept entries without `storyUid`.
- Attachments: the manifest is an array of `Attachment` records in `src/services/attachment-files/attachment-files.ts`. Add an optional `storyUid` to `Attachment`, and keep the manifest validation compatible with old records. `src/services/attachment/attachment.ts` creates the records.
- Obey the lock order: never take the Project write lock while you hold the state lock.
- Keep the Pi SDK behind `src/services/pi-runtime/`.

## Assumptions

- The key name is `storyUid` in each record. Reason: the records already use `storyId` (or `story`), and the two keys are then easy to compare.
- `dependsOn` and Spec links keep only the Story ID. Reason: people write and read them in the Story and Spec files, and a UUID there makes the files hard to read.
- The attachment manifest keeps `storyUid` on each attachment record, not at the top of the file. Reason: the manifest is an array of records today, and a change of the file shape breaks old readers.
- Only the reads in `## Scope` use the resolver. Reason: these reads find the Story of a record. The other ID comparisons do not need a change before ROW-115, and a smaller change fits one pull request.
- When a `storyUid` matches no Story, the read uses the Story ID. Reason: the author asked for a fallback to the Story ID, and a record must not get lost because its Story has no `uid` yet.
