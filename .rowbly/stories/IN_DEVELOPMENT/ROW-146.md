## Goal

`TagsSection` and `CustomFieldsSection` in Settings are almost the same file. Only the names, the service calls, the row component, the form modal and the confirm text are different. Put the shared list/new/edit/remove logic in one generic `CrudListSection<T>` component and use it in both sections. The user sees no change in behaviour. The code gets smaller (about 140 lines less) and easier to maintain.

## Scope

In scope:

- A new generic component `CrudListSection<T>` in `src/tui/screens/settings/crud-list-section/` (`crud-list-section.tsx` and `index.ts`).
- Rewrite `src/tui/screens/settings/tags-section/tags-section.tsx` and `src/tui/screens/settings/custom-fields-section/custom-fields-section.tsx` as thin wrappers around `CrudListSection<T>`.

Not in scope:

- Changes to `TagRow`, `CustomFieldRow`, `TagFormModal`, `CustomFieldFormModal`, the services or `settings-sections.ts`.
- Changes to other Settings sections (stages, prompts, hosts, skills). They do not use the same list/new/edit/remove mode.
- Changes to visible text, keys, hints or toasts.

## Acceptance criteria

- [ ] `src/tui/screens/settings/crud-list-section/crud-list-section.tsx` exports `CrudListSection<T>`, and `crud-list-section/index.ts` exports it with `export * from "./crud-list-section.js";`.
- [ ] `tags-section.tsx` and `custom-fields-section.tsx` use `CrudListSection` and do not define their own `Mode` type, env interface, key handler, `done`, `removed` or `removeFailed` functions (`grep -n "type Mode" src/tui/screens/settings/tags-section src/tui/screens/settings/custom-fields-section` gives no result).
- [ ] The total line count of the two section files plus the new component is less than the 346 lines of the two section files before the change.
- [ ] `TagsSection` and `CustomFieldsSection` keep the same exported names and the same `SettingsSectionProps` signature. `settings-sections.ts` does not change.
- [ ] All visible text stays the same for each section: the loading label (`Loading Tags…` / `Loading Custom Fields…`), the empty text (`No Tags. Press n to add one.` / `No Custom Fields. Press n to add one.`), the button label (`+ New Tag` / `+ New Custom Field`), the hint `new Tag` / `new Custom Field`, the confirm title (`Remove Tag › <value>` / `Remove Custom Field › <label>`), the confirm message and the toast `Removed <label>`. A person can examine this in the TUI.
- [ ] The keys stay the same: `↑/↓` select, `n` new, `enter` or `e` edit, `d` remove with a destructive confirm dialog. A click on a row edits it. The `enter`/`d` hints show only when a row is selected. The keys and hints are off while a modal or dialog is open. A person can examine this in the TUI.
- [ ] After a save or a remove, the section goes back to the list, reloads the items and calls `onChange`. A failed remove shows an error toast and goes back to the list.
- [ ] Custom Field rows still line up with both the label column and the key column.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

- Current files: `src/tui/screens/settings/tags-section/tags-section.tsx` (169 lines) and `src/tui/screens/settings/custom-fields-section/custom-fields-section.tsx` (177 lines). Both are registered in `src/tui/screens/settings/settings-sections.ts`.
- Proposed props of `CrudListSection<T>` (the developer can change the names):
  - `ctx`, `onChange` (from `SettingsSectionProps`).
  - `noun: string` — `"Tag"` / `"Custom Field"`. It gives the loading label (`Loading ${noun}s…`), the empty text, the button label, the hint and the confirm title prefix.
  - `load: (ctx) => Promise<T[]>` — `listTags` / `listCustomFields`.
  - `remove: (item, ctx) => Promise<unknown>` — `removeTag({ value })` / `removeCustomField({ key })`.
  - `itemKey: (item) => string` — `tag.value` / `field.key`.
  - `itemLabel: (item) => string` — used in the `Removed <label>` toast and the confirm message.
  - `confirmTitle(item)` or a title value function — the tag section shows `value`, the field section shows `label`.
  - `confirmMessage: (item) => string`.
  - `renderRow: (item, { selected, active, onClick }, items) => ReactNode` — the caller computes its column widths with `columnWidth` (Custom Fields needs `labelWidth` and `keyWidth`). Alternatively pass the list of items to the render function so the caller can compute widths.
  - `renderForm: (item | undefined, { onClose, onSaved }) => ReactNode` — `TagFormModal` / `CustomFieldFormModal`.
- Keep the module-level handler pattern with an env object (see `.agents/skills/rowbly-code-style/SKILL.md`, React components). Use the hooks from `src/tui/hooks/index.js`: `useAsync`, `useCursor`, `useIsActive`, `useKeyHints`, `useToast`, `showToast`. Use `Button`, `ConfirmDialog`, `Loading` from `src/tui/components/index.js` and colours only from `theme`.
- `useAsync(() => load(ctx), [ctx])`: keep the dependency list on `ctx` only. Do not add `load` to the dependencies if the caller passes an inline function, or the list reloads on each render.
- Keep the JSDoc of each section that describes its keys. Move the shared parts of the text to `CrudListSection`.
- Read `.agents/skills/rowbly-tui-design/SKILL.md` and `.agents/skills/rowbly-code-style/SKILL.md` before the work. Do not write TUI tests (AGENTS.md rule 4).
- `docs/architecture/tui.md` (the Tags section text near line 573) describes behaviour that does not change. Update it only if it names the internal structure.

## Assumptions

- The shared component goes in `src/tui/screens/settings/crud-list-section/`, not in `src/tui/components/`. Reason: only the Settings screen uses it, and `docs/architecture/tui.md` puts screen-specific parts in `screens/<area>/`.
- Use a generic component `CrudListSection<T>`, not only a `useCrudList<T>` hook. Reason: the JSX (loading, empty text, button, modal, dialog) is also the same, so a component removes more duplicate code. A small internal hook is permitted if the code style needs it.
- The confirm titles stay different (the Tag title uses the value, the Custom Field title uses the label). Reason: the Story asks for a refactor with no change in behaviour.
