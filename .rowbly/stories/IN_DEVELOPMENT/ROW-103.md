## Goal

The user can see the worker hosts and change the placement policy in the TUI Settings. Today the user must use the CLI and edit `~/.rowblyrc.json` or `.rowbly/rowbly.config.json` to see a host, to change its worker limit or to change the placement.

Read the Spec `remote-worker-hosts`, sections "Setup of a worker host" and "Placement". Read the `rowbly-tui-design` skill and the `rowbly-code-style` skill.

## Scope

In scope:

- A new "Hosts" section in the "Factory" group of Settings, after the Git section (`src/tui/screens/settings/hosts-section/`, registered in `SETTINGS_GROUPS` of `src/tui/screens/settings/settings-sections.ts`).
- A placement card at the top of the section. It shows the `placement` value of the factory settings (`prefer-local` is the default) and lets the user select `prefer-local`, `most-free` or `prefer-remote`.
- A list of the worker hosts, in the order of `~/.rowblyrc.json`. Each row shows: the id, the SSH target, the worker limit, the global on/off switch (`enabled`), whether the host is on for the current Project (`host use`), and the result of the last check.
- Actions on the selected host:
  - Turn the host on or off for the current Project (`useHost` / `unuseHost` of `src/services/host-project/`).
  - Turn the host on or off for all Projects (the `enabled` field).
  - Change the worker limit (`maxWorkers`).
  - Run the check (`checkHost` of ROW-87) and show the items.
- A new service function `updateHost` in `src/services/host/host.ts` that changes `maxWorkers` and/or `enabled` of one host, and a CLI command `rowbly host update <id> [--max-workers <n>] [--enable | --disable]` that calls it. ROW-84 left the change of a host to this Story.
- A record of the last check result in the host entry of `~/.rowblyrc.json`, written by `checkHost`, so that the CLI and the TUI show the same "last check".
- A service function that gives the rows of the list (the host, its use by the current Project and its last check), so that the component has no domain logic.
- Documentation in STE: the Hosts section in `docs/architecture/tui.md`; `host update` in `docs/architecture/cli.md` and `skills/rowbly-reference.md` (then copy it to each `skills/<name>/references/rowbly-reference.md`); the `lastCheck` key of a host in `docs/architecture/storage.md`.

Not in scope:

- `host add`, `host remove` and `host login` in the TUI. They stay in the CLI. `host login` needs a terminal.
- `host use --path` in the TUI. The TUI always uses the managed clone folder. The CLI keeps `--path`.
- The connection state and heartbeat of a host (ROW-97, ROW-100) and the remote Threads on the board (ROW-102).
- The use of `enabled` by the manager or the placement (ROW-96, ROW-97).
- User documentation of remote hosts (ROW-105).

## Acceptance criteria

- [ ] Settings has a "Hosts" section in the "Factory" group, after "Git". With no hosts, the section shows the placement card and an empty-state text that tells the user to run `rowbly host add <id> --ssh <target> --max-workers <n>`. Check this in a real terminal with the `rowbly-screenshots` skill.
- [ ] The placement card shows `prefer-local` for a config without the `placement` key. A selection of `most-free` calls `updateFactorySettings({ placement: "most-free" })` and the config then has the key, and the other keys of the config do not change. Check this in a real terminal, then with `rowbly factory status --json` or by a read of `.rowbly/rowbly.config.json`.
- [ ] With two hosts in `~/.rowblyrc.json`, the section lists both, in file order, with the id, the SSH target, the worker limit, the global switch, "on for this Project" yes/no and the last check ("not checked" before the first check). Check this with the `rowbly-screenshots` skill and a temporary `HOME`.
- [ ] `updateHost({ id, maxWorkers })` writes the new limit and keeps all other keys of the host entry (`projects`, `lastCheck`) and of `~/.rowblyrc.json`. `updateHost({ id, enabled: false })` writes `enabled: false`. A service test examines each case.
- [ ] `updateHost` gives `VALIDATION` for a worker limit that is not an integer of 1 or more, and for an input with no change. It gives `NOT_FOUND` for an unknown id. When `~/.rowblyrc.json` is invalid, it gives `VALIDATION` and the file bytes do not change. A test covers each case.
- [ ] `rowbly host update mini --max-workers 3 --json` prints the changed host. `--enable` and `--disable` together give `VALIDATION`. A CLI test covers this.
- [ ] `checkHost` writes `lastCheck: { "at": <ISO time>, "ready": boolean, "failed": [<ids of fail items>] }` to the host entry after the check, and keeps all other keys. `listHosts` and `host list --json` keep the shape `{ id, ssh, maxWorkers, enabled }`. A service test with the fake transport examines this.
- [ ] A host entry with an invalid `lastCheck` value makes the host commands fail with `VALIDATION`, and the file bytes do not change. A test covers this.
- [ ] The row service gives, for each host, `usedByProject: true` when `hostProjectFor` finds the current Project, else `false`, and `lastCheck` or `null`. Outside a Project, `usedByProject` is `false`. A service test covers this.
- [ ] In the TUI, the action "on for this Project" on a host that the Project does not use calls `useHost`, shows a busy state while the clone runs, and then shows the host as on. On a used host it calls `unuseHost`. An error (for example `HOST_GIT_ACCESS`, or `CONFLICT` for an active Thread) shows its message and hint, and the list does not change. A person examines this in a real terminal (with a fake or a real host).
- [ ] In the TUI, the check action runs `checkHost` with a busy state, then shows each item with its state, its detail and, for a `fail` or `warning`, its action. The row then shows the new last check. A person examines this in a real terminal.
- [ ] The worker limit action opens a form. An invalid value shows the `VALIDATION` message and does not change the file.
- [ ] The section and its hook call only services (`host`, `host-project`, `host-check`, `factory-settings`). No component reads or writes `~/.rowblyrc.json` or the config directly, and no component has validation rules. A person examines this in the review.
- [ ] Opening Settings and the Hosts section does not open SSH and does not load Pi. Only the use and the check actions open SSH. The new service modules are in `src/services/pi-runtime/import-boundary.test.ts`.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

- Base branch: merge `origin/main` first. ROW-87 (`src/services/host-check/`, `checkHost`, `findHost`) must be on the base branch. This Story depends on ROW-87.
- Host registry: `src/services/host/host.ts` (`listHosts`, `addHost`, `removeHost`) and `src/services/host/host-rules.ts` (`Host`, `HostEntry`, `rcHosts`, `hostView`, `validateHostInput`). Validate `lastCheck` in `rcHosts` in the same way as `projects` (an invalid value makes the whole `hosts` value invalid). Keep `hostView` at four fields. Reuse the worker limit rule of `validateHostInput`; do not copy it.
- Writes to `~/.rowblyrc.json` go only through `src/services/user-rc/user-rc.ts` (`readRc`, `writeRc`, `rcPath`). Read the file again just before the write in `checkHost`, because the check takes time (the same pattern as `addHost`). Keep all other keys. Do not write the file when Rowbly cannot read it.
- The last check record: put the write in the `host-check` service (for example a small `recordLastCheck(hostId, check, ctx)` in `src/services/host/`), called by `checkHost`. `runHostCheck` inside `addHost` can record it too, because `addHost` writes the entry after the check. If the host was removed during the check, do not write and do not fail.
- Project use: `useHost`, `unuseHost` and `hostProjectFor` in `src/services/host-project/host-project.ts`. `useHost` without `path` uses the managed folder. The clone can take minutes; the TUI must not block input, and must show a spinner (`src/tui/components/spinner`).
- Row service: for example `hostRows(ctx)` in `src/services/host/host-rows.ts` (or in `host-project`), with `{ host, usedByProject, lastCheck }`. Use `findProject(ctx)` to get the root; outside a Project, no host is used. It reads only local files.
- Placement: `getFactorySettings` / `updateFactorySettings` in `src/services/factory-settings/factory-settings.ts`, and the list of policies in `factory-settings/placement-settings.ts` (ROW-95). Use the exported list for the choices; do not copy the policy names in the component.
- CLI: add `update <id>` to `src/commands/host/host.ts` with `run()` of `src/commands/output/output.ts`. Keep the command thin. Update the `register-commands` test if it lists subcommands.
- TUI patterns: follow `git-section/` (`use-git-section.ts`, `git-actions.ts`, `git-view.ts`, `AiSettingCard`, `FormModal`) and the check list of the AI section (`check-list/`, `check-task/`) for the items of the check. Use `SelectList` or the existing row components for the host list, `Switch` for the on/off values, and only the colours of `theme`. Declare the keys with `useKeyHints`. Each action also works with the mouse, as in the other sections.
- Suggested keys (the developer can change them to avoid a conflict with the Settings keys): `p` placement, `u` on/off for this Project, `e` on/off for all Projects, `w` worker limit, `c` check.
- No TUI tests (see `docs/architecture/testing.md`). Service and CLI tests use `useTestProject`, a temporary `HOME` (`ctx.home`) and the fake transport (`src/services/test-project/fake-host-transport.ts`). No test uses real SSH.
- Screenshots: use the `rowbly-screenshots` skill with a temporary `HOME` that has two hosts in `~/.rowblyrc.json`. Do not run SSH to a real host for the screenshots; the list and the placement card do not need SSH.

## Assumptions

- This Story depends on ROW-87 (`host check`). Reason: "run a check" and "the result of the last check" need `checkHost`, and ROW-87 is in development with an open pull request. A second check implementation would be a copy.
- The last check result is stored in the host entry of `~/.rowblyrc.json` as `lastCheck: { at, ready, failed }`, and `checkHost` writes it. Reason: the list must show the last check after a restart of the TUI, and the CLI and the TUI must show the same value. Only a summary is stored; the full items show only after a check in the current session.
- "Turn a host on or off for the Project" means `host use` and `host unuse` of ROW-88. The global `enabled` switch is a separate toggle in the same row. Reason: the Story text names the Project, and ROW-84 left the change of `enabled` and of the worker limit to this Story.
- A new CLI command `rowbly host update` is in scope. Reason: the TUI and the CLI call the same services, and ROW-84 has no command to change a host.
- The TUI always uses the managed clone for `host use`. Reason: the smallest scope; `--path` is an advanced case and stays in the CLI.
- The Hosts section is in the "Factory" group, after Git. Reason: hosts and placement are factory settings, next to the worker limit of the AI section.
- The placement card is in the Hosts section, not in the AI section. Reason: the placement only has an effect with worker hosts, and the Story puts both in one section.
