## Goal

Eleven Stories (ROW-126 to ROW-136) changed the TUI to make it faster. Run the profile of the performance review again after these Stories are done, and compare the new numbers with the baseline. Record the numbers and the method in the documentation, so that a person can do the profile again later. Make sure that the idle board does not commit React renders between user actions. Write a new Story for each hot spot that stays.

## Baseline (2026-11-16, 125 Stories, 140x38, `agentic-tui` PTY)

| Scenario | Result |
| --- | --- |
| `rowbly --help` | 0.14 s |
| `rowbly story search --json` | 0.22 s |
| `rowbly status --json` | 0.35 s |
| TUI launch to first Story row | 1.5 s |
| CPU busy in a 12 s board session (dev React) | 8.1 s |
| CPU busy in the same session (`NODE_ENV=production`) | 6.6 s |

## Scope

In scope:

- Measure the six scenarios of the baseline table again with the built CLI.
- Examine the idle board for React commits between user actions.
- Add a short `## Performance` section to `docs/architecture/tui.md`. It holds the method, the baseline, the new numbers and the date.
- Create one new Story for each remaining hot spot that is more than 100 ms.

Not in scope:

- Repairs of performance problems in `src/`. Each repair goes into a new Story.
- A profiling script, a commit counter or other instrumentation that stays in the repository. Temporary scripts stay outside the repository.
- Automated performance tests or CI benchmarks.

## Technical notes

- **Base branch.** At refinement time, the worktree branch did not yet include the merge of ROW-136 (`6e7399a0`, PR #323), but `origin/main` does. Merge `origin/main` into the branch before you profile. Do not reset the branch.
- **Build.** `pnpm build` writes `dist/cli.js`. Since ROW-126, the built CLI loads React in production mode when `NODE_ENV` is not set (`src/services/react-mode/react-mode.ts`, `src/cli-main.ts`). For the "dev React" row, start the TUI with `--env NODE_ENV=development`. For the production row, do not set `NODE_ENV`.
- **PTY.** Use the setup of `.agents/skills/rowbly-screenshots/SKILL.md`: an `AGENTIC_TUI_STATE_DIR` of its own, `HOME` in a temporary folder, absolute paths, `--cols 140 --rows 38`. Add `--env NODE_OPTIONS="--cpu-prof --cpu-prof-dir=<dir>"`. Node writes the `.cpuprofile` when the process exits, so quit with `q`. At the end, run `t kill` and `t daemon stop` for this state folder only.
- **Key sequence.** Wait for the first Story row of the board. Then 8 × Down, 2 × Up, Enter, Escape, q. Make the session about 12 s long, the same as the baseline. Put an idle window of at least 5 s between two key presses for the idle check.
- **Project data.** Run the TUI on a copy of the canonical Project (`/home/sgolovine/Projects/rowbly`) in a temporary folder: a `git init` folder with a copy of `.rowbly/rowbly.config.json`, `.rowbly/stories/`, `.rowbly/specs/`, `.rowbly/stages/` and `.rowbly/prompts/`. Do not copy `.rowbly/state.json*` or `.rowbly/runtime/`. Record the number of Stories (the baseline had 125).
- **CLI timings.** Run each CLI command (`node dist/cli.js --help`, `story search --json`, `status --json`) with `-C <copy>` at least 5 times and record the median wall time. Use `hyperfine` if it is installed. Else use the shell `time`.
- **Launch time.** Measure from the `t run` command to the end of `t wait "<ID of the first Story row>"`.
- **CPU busy.** CPU busy = profile duration minus the `(idle)` samples, from the `.cpuprofile`. Summarize the profile with a temporary Node script outside the repository. Group the nodes by the `url` of the call frame: `react-reconciler`/`react`, `ink`, `yoga-layout`, and `dist/cli.js` (Rowbly code in the bundle).
- **Idle check.** In the production profile, look at the samples in the idle window. Count the samples in the React commit functions (`commitRoot` and the functions that it calls) and in Ink `onRender`. Zero samples there means no commit. A `t wait --stable --timeout 5000` that passes on the board also shows that no frame was drawn. Note: the factory status poll (5 s) and the 1 s clocks still run. After ROW-129 they must not commit when the state does not change.
- **New Stories.** Use the command prefix of the Run section: `story create` in `BACKLOG` with the tag `performance`. Give the function, the file, the inclusive time and the scenario in the description.
- **Documentation.** Write the new section in ASD-STE100 Simplified Technical English (`docs/contributing/documentation-language.md`). Put the section after `## Board load` and `## Factory status`, before `## Code organization`, or at the end before `## Related`.

## Assumptions

- The TUI runs on a copy of the canonical Project, not on the live Project. Reason: the live factory writes `.rowbly/` and the TUI can repair duplicate IDs on the first load. A copy keeps the user data safe and gives the same number of Stories.
- The idle check uses the CPU profile and `t wait --stable`, not a commit counter in `src/`. Reason: this is the smallest scope. The Story asks for measurements, not for a code change.
- "Hot spot over 100 ms" means inclusive CPU time of more than 100 ms in the production-mode 12 s session, for code that Rowbly owns or causes. Reason: the production mode is the mode of the users after ROW-126.
- New hot-spot Stories go to `BACKLOG`. Reason: `BACKLOG` is the first Stage of the Project, and each new Story must get its own refinement.
- The CLI timings are the median of at least 5 runs. Reason: the baseline does not give its method, and a median is more stable than one run.
- Different hardware or load can change the numbers. The section records the date and the conditions, and the comparison is approximate. Reason: the baseline machine is not known.
