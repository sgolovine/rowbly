Read the Spec `deterministic-factory`.

## Goal

The manager gives each Stage its class (`work`, `hold` or `invalid`) by a fixed rule and by the factory settings. The supervisor does not classify Stage prompts.

## Now

`classifyPrompt` in `src/services/factory-manager/manager-status.ts` gives `invalid` for an empty prompt and `hold` for `BACKLOG` and `DONE`. For all other Stages, it uses the class that the supervisor stored in `state.json` (`prompts`) for the hash of the prompt. A Stage without a stored class is `unclassified`, and the policy skips its Stories until the supervisor calls `classify_stage`.

## Scope

In scope:

- The rule, in this order:
  1. A class in the new setting `factory.stageClasses` (for example `{ "IN_REVIEW": "hold" }`) applies first. The values are `work` and `hold`.
  2. A Stage with an empty prompt is `invalid`.
  3. The first Stage and the last Stage of the board are `hold`.
  4. All other Stages are `work`.
- The class `unclassified` and the skip reason `stage prompt not classified` go away.
- The manager does not read or write the `prompts` key of `state.json`. An old `state.json` with this key stays valid.
- A CLI option sets and clears the class of a Stage, for example `rowbly factory configure --stage IN_REVIEW --class hold`.
- Remove the supervisor tools `stage_get` and `classify_stage`, the `unclassified` section of the supervisor digest, and the classification rules in `src/config/prompts/SUPERVISOR.md`.
- Update the tests of the policy and the manager, and the docs of the native factory.

Not in scope:

- A TUI control for the setting.
- Other supervisor tools.

## Acceptance criteria

- A new Stage with a prompt gets workers at once, without a supervisor turn.
- A Stage in `factory.stageClasses` with `hold` gets no workers.
- The CHANGELOG tells users that a middle Stage that the supervisor classified as `hold` is now `work` until they set `factory.stageClasses`.
