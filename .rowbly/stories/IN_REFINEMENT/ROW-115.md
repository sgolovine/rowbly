## Goal

When two different Stories have the same Story ID, Rowbly gives the newer Story a new number, and the records of each Story stay with that Story. Today ROW-81 re-numbers a duplicate only when one Story at most has factory state. When the two Stories have factory state, it does nothing, because the attempts, the Threads, the worktree branch and the attachments use the Story ID, and Rowbly cannot know to which Story they belong.

Result: two Story files with the same number and a different `uid` are two Stories. Rowbly re-numbers the newer Story also when the two Stories have factory state. The records with a `storyUid` follow their Story.

## Scope

In scope:

- A duplicate group of files with the same number and a different `uid` is a collision. Select the Story that keeps the ID with the ROW-81 age rule. Factory state does not block the repair when each Story of the group has a `uid`.
- Before the re-number, write the values that Rowbly calculates from the Story ID into the frontmatter of the Story that gets a new number, if they are not there:
  - `worktree`: the default path `<root>-worktrees/<ID>`, but only if this folder exists.
  - `branch`: `story/<ID>`, but only when the Story has no `pull_request` and the branch exists.
  Then the Story uses the same worktree and branch after the re-number.
- Read the `branch` frontmatter key in `src/services/worker-worktree/worker-worktree.ts` before the `story/<ID>` default.
- Move the entries of the attachment manifest that have the `storyUid` of the re-numbered Story to `attachments/<new ID>/`. The other entries stay.
- Records with the `storyUid` of the re-numbered Story need no change, because a read finds the Story by `storyUid`.
- Records without `storyUid`, `dependsOn` lists and Spec links stay with the Story that keeps the ID. The notice lists them, so that the user can correct a reference.
- When a Story of the group has no `uid`, use the ROW-81 rules as today.
- The repair does not run while a Story of the group has a running attempt. It reports the group as not repaired, and the next board load or `doctor --fix` tries again.

Not in scope:

- Copies of the same Story (the same `uid`). See the Story "Remove the old copies of a Story that is in two Stage folders".
- A rename of the Git branch or of the worktree folder.
- A change of the GitHub pull request.

## Acceptance criteria

- [ ] A service test: two Stories with the same number, a different `uid` and factory state: the newer Story gets the next free number, and the older Story keeps the ID.
- [ ] A service test: the re-numbered Story without `worktree` and `pull_request` gets `worktree` and `branch` in its frontmatter, and the worker worktree service then uses them.
- [ ] A service test: an attempt and a Thread with the `storyUid` of the re-numbered Story find the new Story ID after the repair.
- [ ] A service test: attachment entries with the `storyUid` of the re-numbered Story move to the folder of the new ID. The other entries do not move.
- [ ] A service test: with a running attempt for the Story ID, no file changes, and the result reports the group as not repaired.
- [ ] A service test: a group with a Story without `uid` uses the ROW-81 rules.
- [ ] A doctor test: `doctor --fix` reports the re-number and the references that stayed with the Story that keeps the ID.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

- `src/services/story-renumber/duplicate-plan.ts` `decideGroup()` has the factory state rule (`hasFactoryState`). `renumber-file.ts` writes the new file with an exclusive create.
- `src/services/worker-worktree/worker-worktree.ts`: `requiredBranch()` gives `story/<ID>` without a pull request, and `worktreePath()` gives `<root>-worktrees/<ID>` without a `worktree` key.
- `src/services/project/project.ts` `renameStoryKey()` and `moveAttachmentDirs()` move attachment folders for a new Project key.
- Read the attempts without the state lock to find a running attempt. Never take the Project write lock while you hold the state lock.

## Assumptions

- A running attempt blocks the repair. Reason: a running worker can write the Story file or its attachments during the re-number.
- The repair does not rename the branch or the worktree folder. Reason: a running Thread or a person can use them. The frontmatter keeps the old names, and they still work.
