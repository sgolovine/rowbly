## Goal

Make the factory start faster. Now `rowbly factory start` fails with "Factory readiness timed out", but the daemon starts and becomes ready after approximately 60 s. The start waits only 15 s (`waitForReady` in `src/services/factory/factory.ts`). Most of the start time is the recovery of the Threads.

## Problem

- `recoverFactory` (`src/services/factory-recovery/factory-recovery.ts`) calls `recoverThread` for each Thread in `.rowbly/runtime/threads/`. Each call does `assertFactoryOwnership`, and then `projectNativeAttempt` (`src/services/thread/thread-projection.ts`).
- `projectNativeAttempt` calls `updateFactoryState` one time for each Thread. Each call takes the state lock, reads and parses `.rowbly/state.json`, and writes the full file again with `durable: true`. It writes the file also when the attempt did not change.
- Measured on this Project: 689 Threads, `state.json` is 1.2 MB with 664 attempts. One update with no change takes approximately 26 ms. 689 updates take approximately 18 s for each recovery.
- The start recovers two times (`recover()` in `src/commands/factory-runner/factory-runner.ts` and `recoverAndConfigure` in `src/services/factory-manager/factory-manager.ts`). Thus the recovery takes approximately 36 s. A different Story can remove the second recovery.
- The time increases with each new Thread.

## Scope

In scope:

1. Project the attempts of all Threads in one `updateFactoryState` call during recovery. Read each Thread one time. Do not take the state lock one time for each Thread.
2. Write `state.json` only when the projection changes an attempt. Keep the attempts that do not change as they are.
3. Keep the order and the result of the recovery the same: interrupt the Threads of a dead owner first, as now, and then project the attempts. A Thread on a worker host keeps its status.
4. Keep the ownership check. One check before the batch write, under the state lock, is sufficient. Do not take the Project write lock while you hold the state lock.
5. The batch write must be safe to do again after a crash, as the current projection is.

Not in scope:

- The second call of `recoverFactory` during a start.
- A change to the 15 s wait limit of `waitForReady`.
- Removal or archive of old Threads or old attempts.
- The speed of the first factory pass after recovery.

## Acceptance criteria

- [ ] One recovery of a Project with 689 Threads and a 1.2 MB `state.json` writes `state.json` not more than one time. A test examines the count of writes with many Threads.
- [ ] A recovery with no changed attempts does not write `state.json`.
- [ ] The tests of `factory-recovery` and `thread-projection` pass with no change to the expected attempts. Add a test for a recovery with a mix of active, completed, remote and non-worker Threads.
- [ ] `projectNativeAttempt` for one Thread operates as before for the other callers.
- [ ] On this Project, the time from the owner lock to the `starting` log event is less than 10 s. Record the time before and after the change in the PR.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.
