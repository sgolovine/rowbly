## Goal

`SearchableSelect` and `SearchableMultiSelect` have the same code to open the fuzzy picker. Move this code into one hook, `usePickerField`. The two fields must keep the same behaviour. The result is less duplicated code (about 50 lines fewer) and one place to change the picker field behaviour.

Files:
- `src/tui/components/searchable-select/searchable-select.tsx` (125 lines)
- `src/tui/components/searchable-multi-select/searchable-multi-select.tsx` (172 lines)

Duplicated code:
- `isQueryText` is the same, word for word.
- `PICKER_HINTS` is different only in the `enter` description: "choose" and "add".
- `openPicker` (`Modal` + `SearchableSelectPicker`). The modal title is different: `Find <label>` and `Add <label>`.
- The setup: `useMainOverlay`, `useContext(LayerWrapContext)`, `useId`, `useState<ReactNode>(null)` for the picker, `useLatest(onChange)`, the `useEffect` that calls `overlay.open(id, picker)` / `overlay.close(id)`, and `useKeyCapture(focused && !picker)`.
- The key handler: return early on `ctrl` / `meta`, `enter` opens the picker with an empty query, and typed text opens the picker with that text as the query.
- The render of `{!overlay && picker}`.

## Scope

In scope:
- A new hook `usePickerField` that holds the shared code above.
- Changes to `SearchableSelect` and `SearchableMultiSelect` so that they use the hook.
- `SearchableMultiSelect` keeps only its own logic: `←/→` cursor, `backspace` / `delete` removal, the `✕` click removal, the `+ add` button, and `pickerOptions` (the options that are not chosen).

Not in scope:
- Changes to `SearchableSelectPicker`, `Modal`, `MultiSelectItem` or `AddOptionButton`.
- Changes to the behaviour, the keys, the hints text or the modal titles.
- Changes to the callers (`field-value.tsx`, `overlay-host.tsx`).

## Technical notes

- Proposed API from the author: `usePickerField({ field, options, value, title, verb, hideSelected, onPick })` returns `{ picker, open(query), inline, keyHandler(input, key) }`.
  - `options`: the options of the picker. The single select gives `field.options ?? []`; the multi select gives `pickerOptions(field, value)`.
  - `value`: the selected value of the picker. The single select gives its value; the multi select gives `null`.
  - `title`: the full modal title, or `verb` makes it. The hint `enter` description comes from `verb`.
  - `onPick(option)`: called with the chosen option. The hook closes the picker after it. The hook keeps the latest `onPick` with `useLatest`.
  - `inline`: the node to render in the field, `!overlay && picker` (`null` when an overlay shows the picker).
  - `keyHandler(input, key)`: returns `true` if it used the key (opens the picker), so that the multi select can handle its other keys first or after.
- The hook needs `focused` too, for `useKeyCapture(focused && !picker)` and for the `isActive` of `useInput`. Add `focused` to the arguments.
- Key order in the multi select must stay: `ctrl`/`meta` return, `enter`, `backspace`/`delete`, `←/→`, then query text. `isQueryText` is false for `backspace`, `delete` and arrows, so the shared handler can check `enter` and query text and the multi select can check its keys when the shared handler did not use the key.
- `AddOptionButton` calls `open("")` from the hook.
- Obey `.agents/skills/rowbly-code-style/SKILL.md`, section "React components": top-level functions with an `env` object, handlers as one expression, refs only through `useLatest` / `writeRef`. Obey `.agents/skills/rowbly-tui-design/SKILL.md`.
- Use `.js` extensions in relative imports. File and folder names are dash-case.
- Do not write TUI tests (AGENTS.md rule 4).
- If `docs/architecture/tui.md` lists the component files or hooks, add the new hook there in STE.

## Assumptions

- The hook goes in `src/tui/components/searchable-select-picker/use-picker-field.tsx`. Reason: both fields already import `SearchableSelectPicker` from that folder, and the code style puts a hook in the folder of the component that it serves. `src/tui/hooks/` is for hooks that all of the TUI shares.
- The hook takes a `focused` argument that the author's API does not list. Reason: `useKeyCapture` and `useInput` need it.
- The developer can let the hook call `useInput` itself and take an optional handler for the other keys, in place of returning `keyHandler`, if that agrees better with the code style. Reason: the goal is to remove duplicated code, not a fixed API shape. The behaviour criteria do not change.
