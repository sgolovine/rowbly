## Goal

Sometimes the native factory does not start a worker for a Story in a Stage where it must have a worker. Today the user must move the Story out of the Stage and back to make the factory "wake up" and evaluate the Story again. The user needs one control in the Story view that forces the factory to evaluate the Story for a worker again, with the same effect as a Stage round trip (for example to Backlog and back).

Original request (kept for reference): "Investigate why this is happening and issue a fix. Add a button to the story view. When in an eligible column, there should be a button at the top of the page that a user can press and force the supervisor to evaluate that story for assignment. Should essentially do the same thing as moving the story to the backlog and then back."

## Scope

In scope:

- A "force assignment" operation in the native factory: a service function, the daemon control command and the CLI command.
- A `Force assignment` Button at the top of the Story view in the TUI, for an eligible Story.
- Tests and documentation for the changed services and command.

Not in scope:

- The investigation and the repair of the root cause. This is ROW-161.
- The right-click context menu of a Story. This is ROW-159. ROW-159 uses the operation of this Story.
- A change to the policy limits (`DEFAULT_LIMITS`) or to the scan interval.

## Acceptance criteria

- [ ] A service function in `src/services/factory/factory.ts` sends a control command to the live daemon that forces the evaluation of one Story. Without a live daemon, it gives `CONFLICT` with `Factory is not running`. A Story ID that is empty or longer than 128 characters gives `VALIDATION`.
- [ ] In the daemon, the operation on a Story in a work Stage with no active worker removes its `parked` entry, its `nativeCancelled` entry and its `launchFailures` entry, resets its attempt budget, and marks its last stopped attempt as a Stage departure. Then it requests a new pass (`notify`). A unit test shows that the next `evaluateScan` gives the action `start` with the reason `new stage stay` for a Story that was `parked`, in `retry delay`, in `launch delay` or `cancelled by user`.
- [ ] The operation does not start a second worker: a Story with an active worker, or with an attempt that is not stopped, stays skipped. A unit test shows this.
- [ ] The operation does not change the Story file and does not move the Story.
- [ ] The receipt tells whether the operation changed the state (`released: true` or `false`) and has `storyId`. A Story that does not exist, that is not in a work Stage, or that has an active worker gives `released: false` and no state change.
- [ ] `rowbly factory release <story-id>` does the operation for each Story, not only for a parked Story. A command test shows the JSON output.
- [ ] In the TUI, the Story view shows a `Force assignment` Button at the top when the factory is live, the factory status has a queue entry for the Story (`queueEntry` in `src/tui/screens/factory/factory-status.ts`) and the Story has no pending or running Thread. In other conditions the Button does not show. A person examines this in a real terminal.
- [ ] A click on the Button, or its key, sends the operation. A success shows an `info` toast. A failure shows an error toast with the reason. A person examines this in a real terminal.
- [ ] The operation does not load Pi.
- [ ] `docs/architecture/native-factory/controls.md` and `docs/architecture/native-factory/recovery.md` describe the new behaviour. `packages/cli/skills/rowbly-reference.md` describes the changed `factory release` command, and each copy in `packages/cli/skills/<name>/references/` is the same.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

- Existing parts to extend:
  - `releaseFactoryStory` in `src/services/factory/factory.ts` sends the control command `release-story`.
  - `src/commands/factory-runner/control-poller.ts` calls `manager.releaseStory`, which is `releaseParkedStory` in `src/services/factory-manager/story-release.ts`. Today `releaseIfParked` returns `released: false` with no change when the Story is not parked. This is the only reason why the command does not help for the other skip reasons.
  - `releaseStory` in `src/services/factory-policy/policy-records.ts` already removes `parked` and `nativeCancelled`, resets the budget and marks the last departure. It does not remove `launchFailures`. Add this, or do it in `story-release.ts`.
  - `releaseForResume` in `src/services/factory-manager/worker-reservation.ts` uses `releaseStory` too. Do not change its behaviour except for the `launchFailures` removal, if you add it to `releaseStory`.
- Why this equals a Stage round trip: a move to a hold Stage resets the budget (`planStory` in `src/services/factory-policy/factory-policy.ts`), and the return gives `observedStageDeparture`, so `planAttempts` gives `start` with `new stage stay`. The move also changes the Story hash, which releases `parked` and `cancelled by user`.
- Eligibility in the TUI: the status file queue (`persistStatus` in `src/services/factory-manager/manager-status.ts`) leaves out `hold stage` and `stage unavailable`. So a queue entry means that the Story is in a work Stage. The Threads tab already reads the queue entry (`src/tui/screens/stories/threads-tab/`).
- The TUI calls the service through the existing factory hooks. Do not put the logic in a component. Read `.agents/skills/rowbly-tui-design/SKILL.md` and `.agents/skills/rowbly-code-style/SKILL.md` first.
- Take only the state lock in the daemon. Never take the Project write lock while you hold the state lock.
- Update `src/services/factory-manager/factory-manager.test.ts` or add a test next to `story-release.ts`, and `src/commands/factory/factory.test.ts`. Do not write TUI tests.

## Assumptions

- The Story is split. This Story holds the force-assignment control. ROW-161 holds the investigation and the root-cause repair. Reason: the cause is not known, and the control is a complete result of its own that ROW-159 needs.
- The operation extends the existing `release-story` control command and `rowbly factory release`, and does not add a new command. Reason: `releaseStory` already does almost all of the work, and this is the smallest change.
- The operation does not move the Story to Backlog and back. It changes only the factory state. Reason: a real Stage move changes `updatedAt`, the board order and the Git history, and the factory state change gives the same scheduling result.
- The Button shows only while the factory is live. Reason: without a live daemon, nothing can start a worker, and the service gives `CONFLICT`.
- The Button label is `Force assignment`. The developer selects a key that the Story view does not use, and shows it in the key hints. Reason: the author did not give a label or a key.
- A Story that does not exist gives `released: false`, not `NOT_FOUND`. Reason: the existing release of a Story that is not parked gives a success with no change, and this keeps the receipt rules of the control command.
- "Eligible column" means a work Stage, which the queue entry shows. Reason: only a work Stage gets workers.
