## Goal

Decrease the CPU time that the Pi SDK preload uses when the TUI starts. The profile of ROW-137 found a hot spot in the Pi worker thread.

The main thread of each Rowbly process turns on the Node compile cache (`src/cli.ts`). A `worker_threads` worker does not get this cache. A test on Node 24.22.1 showed that `getCompileCacheDir()` is `undefined` in a worker after the main thread called `enableCompileCache()`. Thus the Pi worker compiles all of the Pi SDK again on each start of the TUI. The result for the user: the TUI uses less CPU after it starts, and the model list and the provider status come faster after the first start.

## Hot spot

- Function: `loadPi` and `createFactoryRuntime` (`src/services/pi-runtime/`), in the Pi worker thread that `warmPiWorker` (`src/services/pi-runtime/pi-worker-client.ts`) starts through `preloadPiSdk` in `src/cli-main.ts`.
- Inclusive CPU time: 518 ms in the worker thread (median run, range 510 ms to 632 ms). The worker thread is busy for 801 ms in total.
- Most of the time is module resolution and compile (`compileSourceTextModule`, `realpathSync`, `resolveSync`, `package_json_reader`).
- Scenario: the production-mode 12 s board session of ROW-137 (`docs/architecture/tui.md`, `## Performance`). 138 Stories, 140x38, Node 24, `NODE_ENV` not set.
- The work is off the render thread. The main thread does not wait for it. But it uses one CPU core for about 0.5 s on each start of the TUI, also when the user does not open a Pi feature.

## Scope

In scope:

- Turn on the Rowbly compile cache in the Pi worker thread, before the worker imports Pi.
- A test for the change.
- Measure the worker thread again and record the numbers.
- Update the docs of the Pi worker and of the compile cache.

Not in scope:

- A change to the time or the trigger of the preload (`usePiPreload`, `PI_PRELOAD_DELAY_MS`, `preloadPiSdk`). See `## Assumptions`.
- A change to the module resolution of Pi (`realpathSync`, `resolveSync`). The compile cache does not decrease this time.
- The launch time of the main thread. ROW-139 has that work.

## Technical notes

- `src/services/pi-runtime/pi-worker.ts` is the worker entry. The serve branch at the end of the file (`!isMainThread && parentPort && isPiWorkerData(workerData)`) is the correct place for the call, before `serve(parentPort)`. Only the worker thread that the client starts runs this branch.
- The static imports of `pi-worker.ts` (`agent-auth`, `factory-runtime`, `errors`, `pi-worker-protocol`) do not load Pi. `loadPi` in `pi-runtime.ts` loads Pi with a dynamic `import()`. Thus a call in the module body is early enough for the Pi SDK.
- `pi-worker.ts` is a second tsup entry (`dist/pi-worker.js`). `pnpm dev` runs `pi-worker.ts` with tsx and the loader flags of the main process.
- Node writes the compile cache of a worker also when the client calls `terminate()`. A test on Node 24.22.1 showed one cache file after `terminate()` with no call to `flushCompileCache()`. If the measurement shows no cache entries for Pi, call `module.flushCompileCache()` after the first answer of the worker.
- `enableRowblyCompileCache()` never throws and never writes output. Keep the worker output dropped, as `startWorkerThread()` in `pi-worker-client.ts` does now.
- Keep the Pi SDK behind the lazy boundary in `src/services/pi-runtime/`. The board, help, doctor, status and history paths must not load Pi.
- The `## Performance` section of `docs/architecture/tui.md` comes from ROW-137 (branch `story/ROW-137`, stage `IN_REVIEW`). It is not on `main` at the time of refinement.

## Assumptions

- Only the compile cache is in scope. The idea "start the preload later, or only when the user opens a view that needs Pi" is not in scope. Reason: the preload exists so that the Models tab and the Factory controls do not wait for Pi. A later preload changes this behaviour. The compile cache keeps the behaviour and has the smallest scope. A person can create a new Story for a lazy preload if the new numbers are not sufficient.
- There is no fixed numeric target. The busy time of the worker thread with a warm cache must be less than the baseline of 801 ms in the same scenario. Reason: the Story gives no target, and the numbers change with the hardware.
- If `## Performance` is not in `docs/architecture/tui.md` on `main` when the work starts, merge `origin/main` first. If ROW-137 is still not merged, record the numbers only in the pull request and in the CHANGELOG entry. Reason: the Story must not wait for a different Story.
