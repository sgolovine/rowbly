## Goal

Each Story gets a permanent identity that does not change when its number changes. Today the Story ID (for example `ROW-78`) is the only identity of a Story. When two Story files have the same number, Rowbly cannot know if they are two different Stories or two copies of the same Story. It also cannot know to which of the two Stories a factory attempt, a Thread or an attachment belongs.

Result: each Story file has a `uid` frontmatter key with a UUID. Rowbly writes it when it creates the Story, and never changes it.

## Scope

In scope:

- `createStory` writes `uid` (a random UUID v4) in the frontmatter of each new Story.
- The Story service reads `uid` and gives it in `Story` (`rowbly --json story get` and `story search` show it).
- An update, a Stage move, a re-number (`project update --key`, the doctor fix of a duplicate Story ID) keeps the `uid`. Nothing writes a new `uid` for a Story that has one.
- `rowbly doctor` accepts `uid` as a known frontmatter key. Today `unknownKeyIssues` reports each key that is not known as an error, and `--fix` removes it.
- `rowbly doctor` reports each Story without a `uid` as a warning. `rowbly doctor --fix` adds a new `uid` to it.
- `rowbly doctor` reports an invalid `uid` (not a UUID string) as an error without a fix.
- A custom field cannot use the key `uid`.
- Update `docs/architecture/storage.md` (the Story frontmatter keys and the doctor table) and `skills/rowbly-reference.md`. Copy the reference to each `skills/<name>/references/rowbly-reference.md`.

Not in scope:

- The use of `uid` in other records (see ROW-113, ROW-114 and ROW-115, which depend on this Story).
- The repair of duplicate Story IDs.
- A `uid` in the TUI. The user does not see it.
- A CLI flag that sets or changes a `uid`.

## Technical notes

- `src/services/story/story.ts` `newStoryData()` builds the frontmatter of a new Story. Add `uid: randomUUID()` (from `node:crypto`).
- `src/services/story/story-types.ts` `Story`: add an optional `uid?: string`. `src/services/story/story-read.ts` `toStory()` sets it when the frontmatter has a string value.
- `src/services/story-files/story-files.ts` `LEADING_KEYS` gives the order of the frontmatter keys. Put `uid` after `position` and before `dependsOn`, or near `createdAt`. Keep one consistent place.
- `src/services/doctor/story-checks.ts`: add `uid` to the `known` set of `unknownKeyIssues`. Add a `uid` check in the Story check order (follow the `agentLockIssues` and `reportChange` pattern for the fix).
- `src/services/config/config-keys.ts` `RESERVED_FIELD_KEYS`: add `uid`.
- The update paths keep the frontmatter of the file (`updateStoryFields`, `saveStoryFile`), so a `uid` stays. Examine that the outbox apply path (`src/services/outbox-apply/`) and the re-number paths do not rebuild the frontmatter without it.
- Tests: `src/services/story/*.test.ts`, `src/services/doctor/doctor.test.ts` (or a new `story-uid-checks.test.ts`), and the config key tests.

## Assumptions

- The key name is `uid`, and the value is a lower-case UUID v4. Reason: it is short and it does not look like the Story ID.
- Two Story files with the same `uid` are copies of the same Story. Other Stories use this rule.
- `createStory` uses `crypto.randomUUID()` directly. `ServiceContext` gets no random source. Reason: the tests examine the format and that two values are different, so they do not need a fixed value. This is the smallest change.
- The doctor fix for a missing `uid` does not change `updatedAt`. Reason: a `uid` is not a change of the Story content, and a new `updatedAt` changes the order of the Stories in a Stage.
- `uid` is added to the reserved custom field keys. Reason: a custom field with this key would write the same frontmatter key. An existing Project with a `uid` custom field is improbable; this Story does not add a migration for it.
