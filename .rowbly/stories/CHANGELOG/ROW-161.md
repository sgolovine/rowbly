## Goal

Sometimes the native factory does not start a worker for a Story in a work Stage. Today the user must move the Story out of the Stage and back to make the factory start a worker. ROW-158 adds a manual "force assignment" control. This Story finds the cause and repairs it, so that the manual control is not necessary in normal use. When a Story must wait for a correct reason, the user can see the reason.

## Scope

In scope:

- An investigation of each candidate cause in "Candidate causes" below, with a unit test that reproduces each cause that is a defect.
- A repair for each confirmed defect, in `src/services/factory-manager/` or `src/services/factory-policy/`.
- A visible reason for a Story that the dispatch step skips silently (see candidate 1), so that a skip is never silent.
- Updates to `docs/architecture/native-factory/` for each changed behaviour.

Not in scope:

- The force-assignment control (service, control command, CLI, TUI Button). This is ROW-158.
- The right-click context menu of a Story. This is ROW-159.
- A change to `DEFAULT_LIMITS` (attempts, retry minutes, retry cap) or to the 30 second scan interval.
- New TUI screens. The existing queue reason in `rowbly factory status --json` and in the Threads tab is the place to show a reason.

## Candidate causes

Findings from the code (start points, not proof). The developer examines each one, and records the result in the pull request description: "defect, repaired", "correct behaviour" or "not reproduced".

1. **Silent dispatch skip.** `dispatchOne` in `src/services/factory-manager/worker-dispatch.ts` ignores each `ConflictError` from `reserveWorker` and records nothing. The policy decision stays `start` or `retry`, so `rowbly factory status` shows a launch, but no worker starts on each pass. Sources of `ConflictError` are in `worker-reservation.ts` (`Story is not eligible`, `Story already has an active worker`, `Story Stage changed`), `worker-placement.ts` (`Cannot place the worker: ...`, `Remote dispatch is not available`) and `worker-launch.ts`. Note: `reserveWorker` scans again with `maxActive = Number.MAX_SAFE_INTEGER` and with the reservation exemptions, so its decision can differ from the loop decision. Also examine the `requests` map: `forgetFinishedRequest` keeps a request whose Thread is in `getState(manager).active`, and `dispatchRequestId` is `<story>:<stage>:<attempt>`. A new Stage stay after a budget reset can get the same request ID as an earlier worker. A Stage round trip changes the attempt number and the decision, which can explain why the round trip helps.
2. **Attempt not projected as stopped.** Attempts in `.rowbly/state.json` are projections of worker Threads (`src/services/thread/thread-projection.ts`). The policy does not get `harnessWorkers` from the native manager, so an attempt stops only when its Thread gets a final status (`changeThread` in `manager-state.ts`, `completeWorker` and `failWorker` in `worker-end.ts`). If a Thread stays `pending` or `running` after its process ended, the Story gets `worker stop unconfirmed` and the attempt uses a worker slot in `limitWorkers`. Examine the end paths of a worker (normal end, crash, daemon restart, `factory-recovery`) for a path that does not give a final Thread status.
3. **Skip reasons that only a Stage round trip clears.** `parked` (after `DEFAULT_LIMITS.attempts` = 4 workers that stopped without a Stage move), `retry delay` (up to 60 minutes after failures in a row), `launch delay` (`launchFailures`) and `cancelled by user` (`nativeCancelled`, `cancelledReason` in `manager-status.ts`). These are correct behaviour by design. Confirm that each one is visible as the queue reason. Do not change them.
4. **Missed wake-up.** The loop scans each 30 seconds and on each Story file change (`src/services/factory-manager/factory-loop.ts`). `requestPassAfterStop` asks for one more pass after `stop confirmed this scan`. A missed wake-up can cause a delay of 30 seconds at most. It is not a probable cause, but confirm that a pass that throws (`recordReconcileFailure`) does not stop the timer.

## Technical notes

- Main files: `src/services/factory-manager/worker-dispatch.ts`, `worker-reservation.ts`, `worker-placement.ts`, `worker-launch.ts`, `worker-end.ts`, `factory-loop.ts`, `manager-status.ts`, `manager-state.ts`; `src/services/factory-policy/factory-policy.ts`, `policy-records.ts`; `src/services/thread/thread-projection.ts`; `src/services/factory-recovery/factory-recovery.ts`.
- To record a dispatch skip, keep the skip in the manager state (for example a map from Story ID to the last dispatch refusal and its decision), and apply it in `scanStories` or in `persistStatus`, the same way as `cancelledReason` and `pausedReason`. Clear the entry when the decision of the Story changes or a worker starts. Do not write it to `.rowbly/state.json`.
- Use `rowbly factory status --json` (`decisions`, `queue`, `workers`, `threads`) and the attempts in `.rowbly/state.json` to look at a live case. Read these files only. Do not write the live state, and do not run a second factory.
- Take only the state lock in the daemon. Never take the Project write lock while you hold the state lock.
- ROW-158 changes `story-release.ts` and `policy-records.ts` at the same time. Merge `main` before the pull request, and keep the changes of ROW-158.
- Use the faux provider and `useTestProject` for tests (see `docs/architecture/testing.md`). Do not write TUI tests.
- Run the Rowbly runtime binary from the root of the worktree. From `packages/cli/`, tsx cannot find the tsconfig. If `TSX_TSCONFIG_PATH` is set in the worker environment, unset it before `pnpm test`.

## Assumptions

- The live state at refinement time (2026-11-18) showed no stuck Story: all queue entries were `worker stop unconfirmed` for running workers, or `waiting for ROW-158`, with 6 of 6 worker slots in use. So the investigation uses the code and tests, not a live reproduction. Reason: no stuck Story was available to examine.
- If the investigation confirms no defect, the Story is complete with the visible dispatch skip reason and the documented results. Reason: the smallest change that agrees with the intent is that the user can always see why a Story waits; a skip that is silent is the only path in the code where the queue shows a launch but no worker starts.
- The skip reasons by design (`parked`, `retry delay`, `launch delay`, `cancelled by user`) stay. ROW-158 gives the manual release for them. Reason: ROW-158 keeps `DEFAULT_LIMITS` out of scope, and these limits protect against loops of failing workers.
- The dispatch skip reason is kept in memory in the daemon, not in `.rowbly/state.json`. Reason: it is a fact of the current daemon process, and the next pass computes it again.
