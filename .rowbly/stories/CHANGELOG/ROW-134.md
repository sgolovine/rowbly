## Goal

The TUI reads the factory activity again each time the factory writes `.rowbly/state.json`, and also with each board load. `getFactoryActivity` in `src/services/factory-activity/factory-activity.ts` is slow on a large Project:

- `storyActivity` (line 162–164) filters all attempts for each Story. This is O(stories × attempts). On the data root of this Project, that is 125 Stories × 512 attempts.
- The state file is 856 KB. Rowbly parses and checks it on each call, also when the file did not change. The profile showed 156 ms for each load, and 90 ms of that time was in `JSON.parse`.
- The watcher `useFactoryStateChanges` in `src/tui/shell/shell/use-shell-data.ts` (about line 155) calls `loadActivity`, and `loadBoard` (about line 67) calls `getFactoryActivity` after each Story change.

The result for the user: the board refreshes quickly, and a Story change does not parse the state file again when the state file did not change.

## Scope

In scope:

- Group the attempts by Story ID one time for each call. Then look up the attempts of each Story. The match becomes O(stories + attempts).
- Cache the checked state in the service module `factory-activity.ts`. The cache key is the path, `mtimeMs`, `size` and `ino` of the file. An unchanged file is not parsed or checked again.
- Update `src/services/factory-activity/factory-activity.test.ts`.

Not in scope:

- Changes to the TUI hooks, the watchers or `use-shell-data.ts`. The cache stays in the service.
- Changes to the format of the state file, or to how the factory writes it (`src/services/factory-state/state-file.ts`).
- A faster parser, or a partial read of the state file. When the file changes, Rowbly parses it again.
- Changes to the activity rules or to the shape of `FactoryActivity`.

## Acceptance criteria

- [ ] All the existing tests in `factory-activity.test.ts` pass with no change of the expected results.
- [ ] A new test: two calls of `getFactoryActivity` with an unchanged state file parse the file only one time (for example, a `vi.spyOn(JSON, "parse")` count, or a spy on `readFile`), and both calls give the same result.
- [ ] A new test: after the state file changes (new content, and a different size or `mtimeMs`), the next call gives the activity of the new content.
- [ ] A new test: after the state file is removed, the next call gives `status: "missing"`. A cached state does not hide a missing file.
- [ ] A new test: a file that was `unavailable` (for example, invalid JSON) and then becomes valid gives `status: "ok"` on the next call.
- [ ] A new test: the activity of a Story with its attempts between the attempts of other Stories is the same as before (the order of the attempts of one Story is kept, so the `conflict` rule still uses the last attempt).
- [ ] Two calls with the same unchanged file but different `stories` inputs give the activity of each input. The cache holds the checked state, not the result for one Story list.
- [ ] `storyActivity` no longer filters the full attempt list for each Story. A code review can examine this: the attempts are grouped by Story ID one time for each call.
- [ ] A person or a local benchmark (not a CI test) can examine this: `getFactoryActivity` for 125 Stories and 512 attempts runs in under 10 ms after the first read of an unchanged file.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

- File: `src/services/factory-activity/factory-activity.ts`. Its only callers are `loadBoard` and `loadActivity` in `src/tui/shell/shell/use-shell-data.ts`. Do not change the exported API.
- Grouping: build a `ReadonlyMap<string, readonly Attempt[]>` from `checked.attempts` with one pass. Keep the file order of the attempts in each group. Attempts without `story` belong to no group; they are already in `missing`, so the status stays `incomplete`. Then `storyActivity` filters only the group of the Story by Stage (`a.stage === undefined || a.stage === story.stage`). The grouping can be computed one time and kept in the cache entry with the checked state.
- Cache:
  - Before the read, `stat` the path. If `stat` fails with `ENOENT`, give `missing`. For other errors, keep the current `unavailable` result. Do not cache a `missing` result or a read error.
  - If the key (path, `mtimeMs`, `size`, `ino`) is the same as the cached key, use the cached entry. Else read, parse and check the file, and replace the cache entry.
  - Cache the `CheckedState` (and the grouped attempts) or the `unavailable` result of an invalid file. Do not cache the per-Story result, because the `stories` input changes.
  - A file can change between `stat` and `readFile`. Then the cache has the new content with the old key. The next `stat` gives a different key, so Rowbly reads the file again. This is acceptable.
- Code style (`.agents/skills/rowbly-code-style/SKILL.md`): no `let`, no mutating calls, no `Map.set`. Keep the cache in a module-level `Store` from `src/services/store/store.ts`, as in `src/services/factory-ownership/owner-probe-cache.ts`. Build the group map with `Object.groupBy`/`Map.groupBy` if the target supports it, or with `reduce` and `withEntry`. Keep each function at the top level.
- Tests: use `useTestProject` as the current tests do. Each test has its own Project directory, so the path in the cache key keeps tests separate. To make a sure change of the key in a test, write content with a different size, or use `utimes` to set a new `mtime`.
- The state file is written with a temporary file and `rename` (`state-file.ts` line 127). A new file has a new inode, so `ino` in the key detects a write that keeps the same size and the same `mtimeMs` on a file system with coarse time stamps.
- Do not load the Pi SDK. This module is on the board path.

## Assumptions

- The cache holds one entry (the last path), not a Map of all paths. Reason: the TUI shows one Project at a time, and one entry keeps the memory bounded, as in `owner-probe-cache.ts`.
- The cache key also includes `ino`, in addition to the path, `mtimeMs` and size that the original Story text gives. Reason: the factory replaces the file with `rename`, so `ino` changes on each write. This prevents a stale result on a file system with coarse time stamps, at no extra cost.
- The 10 ms target is examined by a person or a local benchmark, not by a CI test. Reason: a time limit in CI is not stable. The tests check the behavior (one parse for an unchanged file, and a linear group lookup).
- The `unavailable` result of an invalid but unchanged file is cached. Reason: the file did not change, so a new parse gives the same result.
