## Goal

The shipped TUI runs React in development mode. Nothing in `src/` or `tsup.config.ts` sets `NODE_ENV`, so `react/index.js` and `react-reconciler/index.js` load their development bundles. A CPU profile of a 12 s board session showed about 1.1 s in dev-only work (`runWithFiberInDEV`, `logComponentRender`, `addObjectDiffToProperties`). With `NODE_ENV=production`, the React render time fell from 3.2 s to 1.0 s.

The result: `rowbly` (the TUI) loads the production bundles of React and of the React reconciler, and renders faster. The child processes of Rowbly do not get a changed `NODE_ENV`.

## Scope

In scope:

- Load the production React bundles when Rowbly starts the TUI (`rowbly` with no arguments), in the built CLI (`dist/cli.js`) and in `pnpm dev`.
- Keep the value of `NODE_ENV` when the user sets it (for example `NODE_ENV=development rowbly` keeps the development bundles).
- Make sure that the processes and threads that Rowbly starts (the factory watchdog and daemon, the Pi agents and their shell tools, check commands, the Pi worker thread, Git) do not inherit a `NODE_ENV` that Rowbly set.
- Tests for the behaviour.

Not in scope:

- Other performance work of the TUI (other Stories that ROW-137 depends on).
- Changes to the CLI command path. The CLI commands do not load React (see `src/commands/tui-boundary.test.ts`).
- A `define` of `process.env.NODE_ENV` in `tsup.config.ts`. React is an external dependency, so a bundler `define` has no effect on `react/index.js`.

## Acceptance criteria

- [ ] When `NODE_ENV` is not set, the TUI path loads `react/cjs/react.production.js` and `react-reconciler/cjs/react-reconciler.production.js`, and no `*.development.js` file of `react` or `react-reconciler`. A Vitest test examines this in a child process (see Technical notes).
- [ ] When the user sets `NODE_ENV` (for example to `development`), Rowbly does not change it, and React loads the bundle for that value. A Vitest test examines this.
- [ ] After the TUI modules are loaded, `process.env.NODE_ENV` has the value that it had before (not set, or the value of the user). A Vitest test examines this, so that child processes and worker threads do not inherit `production` from Rowbly.
- [ ] The static imports of `src/cli.ts` stay limited to `node:` built-ins and the compile cache module. The existing tests in `src/cli-startup.test.ts` pass.
- [ ] The CLI commands (for example `rowbly --json status`) do not load React. `src/commands/tui-boundary.test.ts` passes.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.
- [ ] Manual check (only a person can do it): `node dist/cli.js` in a real terminal shows the board as before.

## Technical notes

- Entry files: `src/cli.ts` (bootstrap, only `node:` built-ins and the compile cache as static imports) and `src/cli-main.ts`. The TUI path is the `process.argv.length <= 2` branch of `src/cli-main.ts`. It loads the TUI with `await import("./tui/index.js")`. This import loads `ink`, `react` and `react-reconciler` (and `scheduler`) statically. `react/index.js` and `react-reconciler/index.js` read `process.env.NODE_ENV` only one time, when they are first required. After the load, the value has no effect on these modules.
- Recommended design: a small helper (for example `src/services/react-mode/react-mode.ts`, dash-case, with a test next to it) that takes a loader function. It sets `process.env.NODE_ENV = "production"` only when `NODE_ENV` is not set (`??=` semantics), awaits the loader, and then, in a `finally` block, deletes `NODE_ENV` again if the helper set it. `src/cli-main.ts` wraps `import("./tui/index.js")` with this helper. The helper does not print, prompt or exit, and it does not import `react`, `ink` or `commander`.
- Why the value must be restored: `src/services/factory/factory-launch.ts` spawns the watchdog with the default environment (it inherits `process.env`), and the daemon runs Pi agents whose shell tools also inherit the environment. A `NODE_ENV=production` in the shell of an agent changes the behaviour of tools in the user's repository (for example, `pnpm install` and `npm install` skip devDependencies). The Pi worker thread (`src/services/pi-runtime/pi-worker-client.ts`) starts after the board shows, so it also gets the restored environment.
- Test of the bundle selection: in `src/cli-startup.test.ts` (or the test of the helper), start a child Node process (with the `tsx` loader, as the existing tests do) that runs the helper with `() => import("react")` and `() => import("react-reconciler")`. Then it reads the keys of `createRequire(import.meta.url).cache` and prints the loaded `react`/`react-reconciler` `cjs/*.js` file names and the final `process.env.NODE_ENV`. Remove `NODE_ENV` from the environment of the child for the default case (Vitest sets `NODE_ENV=test` in the parent). Run one more case with `NODE_ENV=development`.
- The TUI itself cannot run in the tests (no TTY, and AGENTS.md says do not write tests for the TUI). Thus the tests examine the helper and the wrapper, not a full TUI session.
- Keep the Pi SDK behind the lazy boundary in `src/services/pi-runtime/`. This change does not touch it.
- Follow `.agents/skills/rowbly-code-style/SKILL.md`. Use `.js` extensions in relative imports.

## Assumptions

- Set `NODE_ENV` only around the load of the TUI modules, and restore it after the load, instead of a permanent `process.env.NODE_ENV ??= "production"` at the top of `src/cli.ts`. Reason: the author asked for production React in the TUI. A permanent value leaks into the factory daemon, the Pi agent shells and check commands, and changes the behaviour of the user's tools. React reads the value only at load time, so the restore keeps the performance gain.
- Do not use the tsup `env` or `define` option. Reason: React is external in the bundle, so a build-time replacement does not reach `react/index.js`, and the test build in `src/cli-startup.test.ts` uses `config: false`.
- `pnpm dev` (tsx) also loads production React by default. Reason: the same code path. A developer who wants the React development warnings sets `NODE_ENV=development`.
- The test examines the helper in a child process, not `node dist/cli.js` with no arguments. Reason: the TUI needs a real terminal, and the CLI commands do not load React. The original "Done when" text (`node dist/cli.js` loads the production bundles) is covered by the helper test plus the manual check.
