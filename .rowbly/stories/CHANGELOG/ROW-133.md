## Goal

Each Story action in the TUI (a Stage move, a save or a delete) reads and renders the whole board two times. `story-changes.ts` and `shell-selection.ts` call `env.reload()` after the write. `loadBoard` in `use-shell-data.ts` then runs `hasProject`, `repairDuplicates`, `getProject`, `listStages`, `searchStories` (all Story files) and `getFactoryActivity`. The file watcher (`useStoryChanges`, `QUIET_MS` = 100 ms) then fires for the same write and reads all of it again.

Result: after a Story action, the shell applies the changed Story that the service returns to the board state in memory. The list updates immediately. Only the watcher echo reads the board from disk, so each action reads the Story files one time at most. The duplicate-ID repair runs only on the first load of a Project, not on each refresh.

## Scope

In scope:

- A local patch of the board in `useShellData` for these Story actions, in place of `env.reload()`:
  - `storyPlaced` (one Story moved by a key or a drop) in `src/tui/shell/shell/story-changes.ts`.
  - `markedPlaced` (the moves of the multi-selection) in `story-changes.ts`.
  - `afterDelete` (a delete from the confirmation and from the Story sidebar) in `story-changes.ts`.
  - `showSavedStory` (a Story that the Story sidebar created or saved) in `src/tui/shell/shell/shell-selection.ts`.
- `repairDuplicates` runs on the first load of a Project only.
- Two pure functions that put a Story on the board and remove a Story from the board, in a service module, with a test.

Not in scope:

- Stage changes: `moveStage` (`story-changes.ts`), `showSavedStage` (`shell-selection.ts`) and the `reload` handler of the settings modal and the onboarding keep `env.reload()`. A Stage rename also moves the Stories of the Stage and changes the config, so a local patch is not safe. See Assumptions.
- The changes that a write makes to other Stories (for example, `deleteStory` removes the ID from the `dependsOn` list of downstream Stories, and the `blocks` and `waitingFor` fields of other Stories). The watcher echo applies them.
- The tabs of the Story sidebar (specs, models, attachments) that call their own `env.reload()`. They reload their own data, not the board.
- A change to `useAsync`, to the watcher or to its quiet time.

## Acceptance criteria

- [ ] `src/tui/shell/shell/story-changes.ts` and `src/tui/shell/shell/shell-selection.ts` do not call `env.reload()` after a successful Story move, multi-selection move, delete or Story save. `grep -n "env.reload" src/tui/shell/shell/story-changes.ts src/tui/shell/shell/shell-selection.ts` shows only `moveStage`, `markedFailed` and `showSavedStage`.
- [ ] A failed multi-selection move (`markedFailed`) still calls `env.reload()`. The other error paths keep their current behaviour (a toast; `removeFailed` also closes the overlay).
- [ ] `loadBoard` calls `repairDuplicateStoryIds` only on the first load of the board for a `ctx` (the first load after start, after a Project switch, or after the onboarding creates the Project). A `reload` or a watcher `refresh` of the same `ctx` does not call it.
- [ ] A new pure function puts a Story on a Story list in board order: it removes the old copy with the same ID, puts the Story at the top of its Stage (Stages in the order of the `stages` argument; a Story of an unknown Stage goes after all known Stages), and sets the 1-based `position` of each Story in the changed Stages. The result is equal to the order of `searchStories({})` after the same write.
- [ ] A new pure function removes a Story by ID from a Story list and sets the 1-based `position` of the Stories in its Stage again. An unknown ID gives the same list.
- [ ] The service test of the two functions passes. It examines: a move to a different Stage, a save in the same Stage (the Story goes to the top), a new Story, a Story of an unknown Stage, a delete, an unknown ID, and the positions after each change. For a move and a delete, the test also compares the result with `searchStories({})` on a test Project (`useTestProject`) after the same service call.
- [ ] A multi-selection move applies the moved Stories in the order of the writes, so the Stories keep their relative order in the target Stage, the same as after a full read.
- [ ] Manual check (a person, in a real terminal with the `rowbly-screenshots` skill): a Stage move of one Story with `shift+←/→` or a drop shows the Story in its new Stage at once. The Story stays selected, and the board does not flash a loading state. A delete and a Story sidebar save also update the list at once.
- [ ] Manual check (a person): when a different process changes a Story file, the list still updates through the watcher.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and `pnpm build` pass.

## Technical notes

Files:

- `src/tui/shell/shell/use-shell-data.ts`
  - Add a local patch to `ShellData`, for example `placeStory(story: Story): void` and `removeStory(id: string): void` (use names that do not collide with `placeStory`/`removeStory`/`dropStory` in `story-changes.ts`, for example `putOnBoard` and `takeFromBoard`).
  - `useAsync` has no setter. Keep the patched board in a `useState` next to `useAsync`, with the board that it patched: `{ base: Board; board: Board } | undefined`. The shown board is `local.board` while `local.base === data.data`, else `data.data`. Thus the next full read (the watcher echo, a `reload` or a Project switch) replaces the patch. Two patches before the echo must stack: patch the board that shows, not `data.data`.
  - Keep `withActivity` and the memo of `board` and `shown` (from ROW-130). A patched board has a new `stories` array, so `withActivity` keeps the activity of the patched board until the next read. That is correct, because the activity is by Story ID.
  - `repairDuplicates`: run it only when the `ctx` of the load is not the `ctx` of the last repair (for example, a `useRef<ServiceContext>`). Set the ref only after `hasProject` is true, so the first load after the onboarding also repairs. Update the doc comment of `repairDuplicates` and `loadBoard`.
- `src/tui/shell/shell/shell-state.ts`: add the two patch functions to `ShellEnv`, with doc comments. Keep `reload`.
- `src/tui/shell/shell/use-shell.ts` and `shell-handlers.ts`: pass the patch functions from `useShellData` to the env.
- `src/tui/shell/shell/story-changes.ts`:
  - `storyPlaced`: call the patch with `moved` in place of `env.reload()`.
  - `markedPlaced`: call the patch for each Story of `moved`, in array order (the order of the writes), in place of `env.reload()`.
  - `afterDelete`: remove the Story `id` from the board in place of `env.reload()`. Compute the next selection from `env.view.rows` before the patch, as now.
- `src/tui/shell/shell/shell-selection.ts`: `showSavedStory` puts `story` on the board in place of `env.reload()`.
- The pure functions: put them in the service layer so that they have a test (the tests must not be in `src/tui/`; see `docs/architecture/testing.md`). For example `src/services/story/story-order.ts` with `withStory(stories, stages, story)` and `withoutStory(stories, id)`, and `story-order.test.ts` next to it. Export them from the module that the TUI imports now. They must not import `react` or `ink`.
- The board order: `searchStories` sorts the Story files by `updatedAt` (newest first), then by number (`sortStoryFiles` in `src/services/story-files/story-files.ts`), then by the Stage order (`stageIndex` in `src/services/story/story-read.ts`). `stagePositions` in `story-read.ts` gives the 1-based position in each Stage. The Story list (`storyListRows`) shows the array in its order. Each `updateStory` sets a new `updatedAt`, so a saved or moved Story is at the top of its Stage.
- Follow the `rowbly-code-style` skill: early returns, no domain logic in a component, `.js` extensions in relative imports, dash-case file names.
- Do not add tests in `src/tui/`. The "shell hook tests" of the original text do not exist; commit `385345c5` removed the TUI tests.

## Assumptions

- The pure board-patch functions go in `src/services/story/` with a service test, and the shell hook gets no test. Reason: the original text asks to update the shell hook tests, but `docs/architecture/testing.md` forbids tests in `src/tui/`, and the TUI tests were removed. A service function can have a test.
- Stage changes (`moveStage`, `showSavedStage`, the settings and the onboarding) keep `env.reload()`. Reason: a Stage rename moves Stories and a Stage position change reorders the board, so a local patch would need the logic of the Stage service. This is the smallest scope that agrees with the goal ("a Stage move of one Story"). A new Story can remove this read later.
- The changes that a write makes to other Stories (the `dependsOn` cleanup of `deleteStory`, and the `blocks` and `waitingFor` fields) show only after the watcher echo. Reason: the services return only the changed Story; the echo comes after approximately 100 ms plus one read.
- If the watcher cannot start, the board still shows the patched Stories, but the changes to other Stories show only after the next full read. Reason: this agrees with the comment of `useStoryChanges`, which accepts updates "after the actions of the TUI".
- A duplicate Story ID that a different process makes while the TUI runs is repaired at the next start or Project switch, and `rowbly doctor` reports it. Reason: the author asked to run the repair on the first load only.
- A race of a watcher read that started before the write can show the old board for a short time, until the echo of the write. Reason: the echo always comes after the write, so the board is correct at the end. No more logic is necessary.
- The current error paths stay: `markedFailed` reloads; `placeStory` and `removeStory` show a toast. Reason: the author asked to keep the error paths, and a single failed write did not change a file.
