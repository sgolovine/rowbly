Split from ROW-99.

## Goal

The user can release a remote Thread. A release stops the Thread like a cancel, and it abandons the Thread when its host is offline (the abandon steps of ROW-99, with the reason `release`). But the Story does not stay `cancelled by user`, and the Story does not wait for the old host. The policy can then start a new worker for the Story, for example a local worker, while the old host is offline.

Read the Spec `remote-worker-hosts`, sections "Decisions" (item 10), "Placement" and "Abandoned Threads".

## Scope

In scope:

- **Factory command `release`.** Add `release` to `FactoryCommandType` and `COMMAND_TYPES` in `src/services/factory-control/factory-control.ts`. The control poller (`src/commands/factory-runner/control-poller.ts`) calls a new manager action `releaseWorker(threadId, expectedRunId)`. The command needs a running factory, as `cancel`.
- **CLI.** `rowbly thread release <id>` sends the command through `sendFactoryCommand("release", { threadId })`, as `rowbly thread cancel <id>` does (`registerControl` in `src/commands/thread/thread.ts`). `--json` output through `run()`.
- **Manager action `releaseWorker`.** In `src/services/factory-manager/worker-reservation.ts`, next to `cancelWorker`, with the same run and active checks (`Worker run changed`, `Worker is not active`). The differences from `cancelWorker`:
  - Only a remote Thread (`thread.host` is not `local`) can be released. A local Thread gives a `ConflictError`.
  - The release does not add the Story to `nativeCancelled`. Thus the scan does not give `cancelled by user`.
  - The Thread becomes `cancelled` (with `resumable` as in a cancel), and the executor gets a stop of the kind `release`.
- **Remote stop of kind `release`.** `stopRemote` in `src/services/remote-executor/remote-stop.ts` accepts `"release"`. It sends `cancel-thread` to the host, as a cancel. When the stop cannot reach the host, the Thread becomes abandoned, the `cancel-thread` command goes in the queue of the host, and the wait of the run ends, as for a cancel. The `abandon` callback of the executor input (`remote-types.ts`, `remote-dispatch.ts`) gets the reason, and `abandonThread` / `writeAbandon` in `src/services/factory-manager/abandoned-threads.ts` write `abandoned: { at, reason, appliedSeq }` with `reason: "release"` for a release. A cancel keeps `reason: "cancel"`. All other steps of ROW-99 (stop first, held entries, remote outcome, attention, resume gate) apply to a released Thread without change.
- **Placement after a release.** In `storyFacts` of `src/services/factory-manager/worker-placement.ts`, when the last worker Thread of the Story has `abandoned.reason === "release"`, the Story has no `lastHost`. Thus the affinity rule does not hold the Story for the old host, and the placement policy selects a host from the eligible hosts.
- Tests next to each changed service.
- Documentation in STE: `rowbly thread release` in `docs/architecture/cli.md`; the release in the abandon steps of `docs/architecture/native-factory/README.md` (section "Abandoned Threads"); the `release` reason of the abandoned note in `docs/architecture/storage.md` if the note is described there.

Not in scope:

- The TUI key for a release (ROW-102 or a later Story).
- A release of a local Thread.
- A supervisor tool for a release.
- Changes to the attempt count or the retry delay of the policy.
- The recovery after a restart of the daemon (ROW-117) and the drop of inbound updates (ROW-98).

## Technical notes

- The cancel path today: `cancelWorker` (`worker-reservation.ts`) writes `nativeCancelled[storyId]`, sets the Thread `cancelled`, then calls `control.cancel()`. For a remote Thread, `control.cancel` is `stopRemote(env, threadId, "cancel")` (`remote-executor.ts`). `stopRemote` calls `abandonRun` (`remote-abandoned.ts`) when `submitStop` fails, and `abandonRun` calls `env.input.abandon(threadId, host)`.
- The executor control needs a `release` method (or a cancel with a kind) so that `releaseWorker` can call it. A local executor control does not need it, because a local Thread cannot be released.
- `skipReason` in `src/services/factory-manager/manager-status.ts` gives `cancelled by user` only from `nativeCancelled`. Without that entry, a cancelled Thread is an `interrupted` attempt for the policy, and the first failure retries on the next scan (`retryDecision` in `factory-policy.ts`).
- `placeWorker` in `placement.ts` holds a Story for its `lastHost` when the worktree facts are not known to be pushed and clean. `readWorktreeFacts` reads only the local worktree, so a Story with a remote `lastHost` always waits for that host. The release rule in `storyFacts` removes this hold for a released Thread.
- `isAbandoned`, `AbandonReason` (`"cancel" | "release"`) and the validation of the reason already exist in `src/services/thread/`.
- The TUI `threads-tab-actions.ts` uses `sendFactoryCommand` with `cancel` and `resume` only. Do not change the TUI.

## Assumptions

- A release is permitted only for a remote Thread. Reason: the Spec describes release only for remote Threads, and a local cancel and a new start already give the same result. This is the smallest scope.
- A release while the host is connected is a cancel without the user hold and without an `abandoned` note. Reason: the Spec abandons a Thread only when the host is offline. The normal outbox sync applies the entries of a connected host.
- The new worker after a release uses the placement policy without affinity to the old host, and it does not get the work that is only on the old host. Reason: the goal is a new worker while the old host is offline. The held entries of ROW-99 keep the late board changes for the user.
- A released Thread counts as an `interrupted` attempt for the policy, as a cancelled Thread does. Reason: smallest scope; the policy needs no change.
- The released Thread keeps `resumable` as a cancel sets it, and the resume gate of ROW-99 applies. Reason: same behaviour as a cancel.
- The CLI command is `rowbly thread release <id>`. Reason: the author gave this example, and it agrees with `thread cancel` and `thread resume`.
