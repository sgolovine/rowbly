Split from ROW-92.

## Goal

A remote worker can read an attachment of any Story of the Project, also when the attachment file is not on its worker host. When the file is not in the copy of the Thread or in the attachment cache of the host, the host gets the file from the main machine on the `host attach` channel, puts it in the cache and gives it to the worker. When the host is offline, the read fails with a clear error that tells the worker that the host is offline.

Read the Spec `remote-worker-hosts`, section "The copy and inbound updates".

ROW-92 puts the attachment files of the Story and of its upstream Stories into the copy of the Thread, through the attachment cache of the host. ROW-96 sends the copy from the main machine and opens one `host attach` channel for each host. This Story adds the other attachment files on demand.

The Spec says "PNG". Since ROW-92, an attachment can have any file type (see `docs/architecture/storage.md`, "Attachments"). This Story applies to all attachment files.

## Scope

In scope:

- **A CLI read path.** A new command `rowbly get-attachment <story> <id>` and a service function (for example `getAttachment` in `src/services/attachment/attachment.ts`). It gives the attachment record and the absolute `path` of its file. On the main machine and for a local worker, a missing file gives `NOT_FOUND`, as today. This is the read path that a worker uses before it reads the file with its read tool.
- **The fetch on the host.** In a remote worker context (the CLI has `ROWBLY_OUTBOX`), when the record is in the manifest of the copy but the file is not in the copy:
  1. If the cache of the host agent has the file, the CLI copies it into the copy (`.rowbly/attachments/<story-id>/<file>`) and gives that path.
  2. Else, if the attach channel is live, the CLI writes a fetch request file, and waits until the file is in the cache, a failure answer arrives, or the time limit (default 30 seconds) ends. Then it copies the file into the copy and gives the path.
  3. Else, or after a failure answer or the time limit, the command fails with a `ConflictError` whose message tells the worker that the worker host is offline (or gives the reason of the main machine) and that the attachment is not available on this host.
- **The host side of the channel.** `rowbly host attach` (`src/services/host-agent/host-attach.ts`):
  - It marks the channel as live while it runs (a channel file with its process identity), and removes the mark at the end.
  - At each poll, it reads the fetch requests and sends one `attachment-request` frame `{ type, storyId, id }` for each new request.
  - It reads the frames of the main machine on its input (today `watchInput` drops them). An `attachment-failed` frame `{ type, id, message }` writes the failure answer of the request.
- **The main machine side.** The channel of the remote executor (`src/services/remote-executor/remote-channel.ts`) handles the `attachment-request` frame: it finds the record in the canonical manifest of the Story, reads the file, and uploads it with the existing call `host cache-put <project-id> <id>`. When the Story or the attachment does not exist, the file is larger than 10 MiB, or the upload fails, it sends an `attachment-failed` frame on the channel. One request id gets at most one upload at a time.
- Documentation in STE: `docs/architecture/native-factory/host-agent.md` (the fetch request files, the channel mark, the two new frames), `docs/architecture/cli.md` (`get-attachment`), `docs/architecture/storage.md` ("Attachments"), and `skills/rowbly-reference.md` (`get-attachment`), copied to each `skills/<name>/references/rowbly-reference.md`.

Not in scope:

- Inbound updates to a running copy (ROW-98). A new attachment of the main machine during a run does not go into the manifest of the copy in this Story.
- A reconnect or a queue of fetch requests on the main machine (ROW-97). A request that the host makes while no channel is live fails at once.
- A fetch of a file through the read tool of Pi. Only the CLI read path fetches.
- The removal of old fetch request files and old cache entries.
- The TUI.

## Technical notes

- **Base branch.** At the time of refinement, the worktree is on a detached `HEAD` (`32f0c863`) without the merge of ROW-96 (PR #292, `50c2da9e`). `src/services/remote-executor/` and `fake-host-agent.ts` are not there. Make the branch `story/ROW-110`, then merge `origin/main` first.
- **The host agent folder for the CLI.** The CLI of the worker must find the cache, the fetch folder and the channel mark. Add the variable `ROWBLY_HOST_AGENT` (the absolute agent folder, `hostAgentPaths(...).dir`) to the worker shell `env` in `src/services/host-agent/host-runner.ts`, next to `ROWBLY_OUTBOX` and `ROWBLY_THREAD_ID`. `commandContext` in `src/commands/output/outbox-env.ts` reads it and puts an attachment source in `ServiceContext` (for example `ctx.remoteAttachments`), in the same way as `recorder`. Services do not read `process.env`. Without `ROWBLY_HOST_AGENT`, a remote context has no fetch, and a missing file gives `NOT_FOUND`.
- **Paths.** Extend `hostAgentPaths` in `src/services/host-agent/host-agent-paths.ts` with `fetch` (`<agent>/fetch/`) and `channel` (`<agent>/channel.json`). Folders have mode 0700 and files mode 0600, as the other files of the agent.
- **Fetch request.** One file for each attachment id: `fetch/<id>.json` with `{ version: 1, storyId, id, requestedAt }`, written with `writeFileAtomic`. The failure answer is `fetch/<id>.failed.json` with `{ message }`. A new request removes an old failure answer first. The CLI removes the request and the failure answer at the end of its wait. Two workers that read the same id share one request; the upload is idempotent (`putCachedAttachment` keeps the first file).
- **Cache.** Use `readCachedAttachment` and `hasCachedAttachment` of `src/services/attachment-cache/attachment-cache.ts`. The cache file name stays `<id>.png` for all types. The copy file name is `attachmentFileName(record)`.
- **Channel mark.** `runHostAttach` writes `channel.json` with its process identity (the `Owner` shape of `src/services/factory-ownership/ownership-lock.ts`) after the hello frame, and removes it when the channel ends. The CLI treats the channel as live only when the file exists and the owner probe says that the process is alive. A stale file (dead process) is not live. Take the probe as an optional dependency so that tests can give a fake.
- **Host frames.** Keep the order of `sendChanges`; add the fetch requests after the session lines. Keep the sent request ids in the `SentValues` store, so that one request gives one frame for each channel. A new channel sends each open request again. Parse the input with `decodeChunk` and `parseFrame` of `src/services/host-transport/json-lines.ts`, with `DEFAULT_LINE_LIMIT`. Ignore frames of other types and bad frames.
- **Main side.** In `dispatchFrame` of `remote-channel.ts`, add the `attachment-request` type. Do the work in a new file, for example `src/services/remote-executor/remote-attachment.ts`, with a test next to it. Read the record with `readAttachments(await attachmentDir(paths, storyId))` and the file with `attachmentFileName`. Upload with `connection.transport.upload([connection.rowbly, "host", "cache-put", projectId, id], bytes)`. Send the failure with `channel.send(...)` of the `HostChannel` of the link. The handler needs the `HostConnection` of the host, so keep it with the link (`HostLink`) when `ensureLink` opens the channel. Do not take the Project write lock or the state lock: the handler only reads canonical files.
- **Bytes.** The file never goes in a frame (the frame limit is 1 MiB and an attachment can be 10 MiB). The frames carry ids and messages only.
- **Time limit.** `DEFAULT_ATTACHMENT_FETCH_MS = 30_000`, with a poll of 250 ms. The service takes both as optional inputs for tests.
- **Fake host.** Extend `fake-host-agent.ts` so that the frames that the main machine sends on the fake channel go to the `input` stream of `runHostAttach`, as JSON lines. Today the fake channel does not write them to the input.
- **Safety.** The host never reads `<clone>/.rowbly/`. The main machine serves only an attachment whose record is in the manifest of the named Story. All remote calls go through `HostTransport`; the new code does not use `child_process`. Do not load Pi. Follow the `rowbly-code-style` skill: dash-case files, `.js` imports, one concern for each file, a test next to each new service file.

## Assumptions

- The CLI read path is a new command `get-attachment <story> <id>` that gives the path of the file. Reason: no CLI command reads an attachment today (`open-attachment` starts a desktop application, which a worker host does not have). The Story asks for a read path of the CLI, and a path lets the worker read the file with its read tool.
- The fetch applies to attachment files of all types, not only PNG files. Reason: since ROW-92 an attachment can have any file type, and the cache and the copy already hold all types.
- The CLI and the attach process communicate with files in the agent folder (a fetch request, a failure answer and the cache file), not with a socket. Reason: the host agent already uses durable files for commands and run state, and the attach process already polls the agent folder.
- The main machine sends the bytes with the existing `cache-put` upload call, not in a frame. Reason: a frame has a limit of 1 MiB and an attachment can be 10 MiB. `cache-put` exists (ROW-92) and validates the id and the size.
- The time limit is 30 seconds. Reason: an upload of 10 MiB over SSH must complete, and a worker must not wait long on a host that lost its channel.
- The error of an offline host is a `ConflictError` (`CONFLICT`). Reason: the error classes are `VALIDATION`, `NOT_FOUND` and `CONFLICT`, and the record exists, so the problem is the state of the host, not the input.
- The fetched file also goes into the copy, not only into the cache. Reason: the path that the command gives must stay valid for the run, and the other attachments of the Story are in the copy too.
- The worker learns about `get-attachment` from the reference document and the CLI help. The system prompts do not change. Reason: the smallest scope, and the system prompts are out of the scope of the Story.
- (Development) An `uncertain` owner probe of the channel mark counts as live. Only a `dead` probe makes the channel not live. Reason: a macOS host has no process identity, so its probe always gives `uncertain`, and the fetch would never work there. `liveAgent` uses the same rule.
- (Development) A fetched file whose size is not the `size` of the record gives `CONFLICT`, and the CLI does not write it to the copy. Reason: a bad cache file must not go into the copy.
