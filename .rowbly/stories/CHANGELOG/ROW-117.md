## Goal

A remote Thread continues correctly after a restart of the factory daemon. A remote Thread resumes only on its own worker host. Read the Spec `remote-worker-hosts`, section "Disconnects".

Now, a restart of the daemon marks each active remote Thread `interrupted` with `OWNER_DIED`, and the new daemon does not follow the run that continues on the host. A resume can go to a different host than the host that has the session and the worktree. The automatic network resume examines the worktree path of a remote Thread on the main machine, where it does not exist. After this Story, the new daemon adopts the remote runs. A remote Thread resumes only on its own host, also after a `NETWORK` failure.

## Scope

In scope:

- **Recovery.** `recoverFactory` (`src/services/factory-recovery/factory-recovery.ts`) does not interrupt a worker Thread whose `host` is set and is not `local` (`LOCAL_HOST`). It still repairs the projection (`projectNativeAttempt`) of that Thread.
- **Adoption at start.** Before the first supervisor turn, the new daemon adopts each worker Thread with status `pending` or `running` on a worker host: it takes the ownership of the last run, registers the active worker slot on the host, puts the Story in `waiting for host sync`, and registers a run in the remote executor with the worker events of the manager. It does not send a new `launch` or `resume` command.
- **Ask the host for its runs.** A new hidden request command `rowbly host runs <project-id>` gives the run state (`run.json`) of each Thread that the main machine asks for. The reconnect of a host with adopted runs asks for these run states after it sends the queued commands and before it opens the `host attach` channel again. Thus the existing reconnect order of ROW-97 stays: queued stop and cancel commands first, then the run states, the results and the outbox.
- **Resume on the own host.** A resume (`resumeWorker`, `reserveWorker` with `resumeThreadId`) uses the host of the Thread (`thread.host`, else `local`). It does not use the placement rules to select a host. When that host is not `connected` or has no free slot, the resume gives a `ConflictError`, and a later attempt can succeed.
- **Network resume.** `resumeNetworkThreads` (`src/services/factory-manager/network-resume.ts`) resumes a remote `NETWORK` Thread on its host, only while the host is `connected`.
- Documentation in STE: `docs/architecture/native-factory/recovery.md` (remote Threads are not interrupted, adoption at start), `host-agent.md` (the `host runs` command and the reconnect of adopted runs), the executor section of `docs/architecture/native-factory/README.md` (resume on the own host), and the new hidden command in `docs/architecture/cli.md`.

Not in scope:

- Abandoned Threads and held entries (ROW-99). Inbound updates (ROW-98). The TUI.
- New host states, a new heartbeat, or a change of the command queue of ROW-97.
- A change of the placement rules for new workers (not resumes).
- Adoption when the manager has no remote dispatch (`deps.hostConnection` is not set). See Assumptions.

## Technical notes

- **Recovery.** In `recoverThread`, skip `interruptThread` when `thread.host` is set and is not `LOCAL_HOST`. `sessionFileExists` reads the local runtime folder, so it is not correct for a remote Thread.
- **Ownership of the run.** `cancelWorker`, `steerWorker` and `buildSnapshot` (`manager-status.ts`) compare `runs.at(-1).ownerToken` with the token of the manager. Add a Thread change in `src/services/thread/` (for example `adoptThreadRun(id, { expectedRevision, ownerToken })`) that sets the owner token of the last run. It does not add a run, because `runs.length > 1` means a resume to the executor and to the host.
- **Adoption.** The manager makes its executors in `createFactoryManager` (`factory-manager.ts`). Do the adoption after the manager exists and before `runFactory` starts the first supervisor turn. For each adopted Thread: read its Story, make the worker events with the code of `workerEvents` in `worker-launch.ts` (export a helper; do not copy the code), call `waitForHostSync`, register the `active` entry with the host and a `control` (`workerControl(manager.remote, id)`), and run a task that awaits the adopted run and then frees the slot (`releaseWorker`) and calls `hostSynced`. Use the `serial` queue of the manager for each Thread change.
- **Remote executor.** Add an `adopt(launch, events)` operation to `RemoteExecutor` (`src/services/remote-executor/remote-types.ts`, `remote-executor.ts`). It registers a `RemoteRun` (`newRemoteRun`) without `prepare`, `serve` or `submit`, marks it as adopted, and resolves when the run ends, the same as `launchRemote`. Then it calls the reconnect of the host one time.
- **The command id.** `takeRunFrame` (`remote-run.ts`) takes only the frames whose `requestId` is the `commandId` of the run. The main machine does not keep the command id. The adopted run gets it from the `requestId` of the run state that `host runs` gives, or from the `id` of a queued `launch` or `resume` for the Thread in `commands.json`.
- **No repeated events.** The Thread record already has the worktree and, after the session opened, the session. Set the `sent` values and `sessionOpened` of the adopted run from the first run state so that `worktreeReady` and `sessionOpened` are not sent again for values that the Thread already has. `assignWorktree` changes the Thread to `pending`, which is not correct for a `running` Thread. A result, an activity and the end that arrived while the daemon was off must still go to the manager.
- **Reconnect.** In `remote-reconnect.ts`, `needsReconnect` is already true for a run without a channel. Add the `host runs` step between `sendQueued` and `reopenLink`, only for adopted runs that have no command id yet. A transport error leaves the runs adopted, and the next heartbeat tries again.
- **`host runs`.** Add the request call in `remote-calls.ts`, the command in `src/commands/host/host-run-commands.ts` (hidden, the same as `run-paths`), and the service function in `src/services/host-agent/` that reads `readHostRun` for each requested Thread id. Input: `{ threadIds: string[] }`. Output: `{ runs: HostRunState[] }`. A Thread without `run.json` is not in `runs`. Validate each id with `validRequestId`. Tests use `createFakeHostAgent` (`src/services/test-project/fake-host-agent.ts`) or a `request` handler of the fake transport.
- **Resume on the own host.** In `worker-reservation.ts`, `assertSlotAvailable` calls `placeStory` for all reservations. For a resume, read the Thread first, and check only the host of the Thread: its state (`withHeartbeatStates`, `managerSlots` in `worker-placement.ts`) must be `connected` and it must have a free slot. Give a `ConflictError` with the reason otherwise. `startWorkerTask` already uses `thread.host`.
- **Worktree checks.** `releaseForResume`, `appendResumeRun` (`worker-reservation.ts`) and `networkWaitingThreads` (`network-wait.ts`) do `stat` of `thread.worktree` on the main machine. For a remote Thread, skip the local check. The host runner refuses a resume without its session and worktree (`resumeFacts` in `host-runner.ts`), and the rejected receipt fails the run.
- **Network resume.** A remote run that failed with a connectivity message already gets the code `NETWORK` from `workerFailure` (`network-wait.ts`). In `resumeNetworkThreads`, skip a remote Thread whose host is not `connected`. The `ConflictError` of a full host is not a problem, as now.

## Assumptions

- Adoption occurs only in a manager with remote dispatch (`deps.hostConnection`). Without it, a remote Thread of a dead owner keeps its status and is not adopted. Reason: the production daemon has `hostConnection` (ROW-116), and `rowbly host remove` refuses while a Thread is active. This is the smallest scope.
- The main machine asks the host for its runs with a new request command `rowbly host runs`, not only with the `host attach` channel. Reason: the main machine must get the command id of each run, and it must find a run that does not exist on the host. The channel does not tell that a run is missing.
- An adopted Thread without a run on the host and without a queued `launch` or `resume` becomes `failed` with the new code `HOST_RUN_MISSING`. Reason: this occurs only when the daemon stopped before the launch got to the host. Then the Story can get a new worker through the normal retry rules. Without this rule, the Story waits without an end.
- The owner token of the last run changes to the token of the new manager. No new run is added. Reason: a new run means a `resume` to the executor and to the host.
- A resume checks only the state and the free slots of the host of the Thread, and not the placement rules (affinity, unpushed work, providers). This applies also to a local Thread: it resumes only on `local`. Reason: the session and the worktree of a Thread are only on its host. The Spec says that a remote Thread can resume only on its own host.
- The session file of a remote Thread is on its host. Thus `appendThreadRun` does not look for it on the main machine. The host refuses a resume without it. Reason: without this change, a remote Thread cannot get a new run.
- A remote Thread whose Story does not exist is not adopted. It keeps its status. Reason: the worker events need the Story. This is the most simple option.
- A stop or cancel of an adopted run without a command id goes to the host with the Thread id (it is submitted, or it goes in the queue). Reason: the host can have the run before the main machine knows its command id.
